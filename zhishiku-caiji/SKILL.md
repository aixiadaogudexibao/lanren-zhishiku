# 知识库案例采集（zhishiku-caiji）

## 概述

采集「解决一个案例的完整执行轨迹」，把它落成结构化案例，供后续提炼**执行流模板、知识点、方案与常用指令表**。

**产物是数据集，不是任务清单。** 案例做没做完不是重点；重点是「每条指令 ↔ 真实输出」的对应关系被完整、如实记录下来。一个案例 = 一个文件夹；大步骤拆成文件，大步骤内部的执行流细到具体指令。

写入采用**哨兵写入位**：只在固定的标记处覆盖写入，不读全文，与文件长度无关。

**本 skill 保留完整的任务表能力**：每个案例有编号、`order` 排序、`flag` 状态（待采集 / 采集中 / 归档中 / 完成归档）、`dai`/`hui` 归档，以及 `qingdan.txt` 大步骤清单。采集流程不改动这套任务表，只是把它当作案例的索引层。

## 下游用途（为什么这样设计）

每个 `->` 块都是一条采集样本：

```text
操作 | 位置 | 指令 | 结果 | 结论
```

后续可以：

- 按 `操作` 聚类 → **常用指令表**
- 按 `结论` 提炼 → **知识点 / 方案**
- 按大步骤串起来 → **执行流模板**

所以「原始指令 + 真实输出」的对应关系必须保住。一旦攒写或事后补写，采到的就是回忆/总结，不是原始输出，整份案例作废。

## 下游衔接

采集完成后，案例交给 `zhishiku-tilian` 提炼，再由 `zhishiku-gengxin` 按领域回注。

```text
本 skill（采集） ─▶ zhishiku-tilian（提炼） ─▶ zhishiku-gengxin（按领域回注容器）
```

- 案例归档后（进 `biao/hui/<id>/`），在报告里提示：「已采集 <领域>/<id>，可运行 `zhishiku-tilian` 提炼。」
- **本 skill 不自动调用提炼**：通常你会先攒几个案例再一起提炼；是否立即提炼由用户决定。
- 领域在新建案例时问用户，并记入 `renwu.txt`；下游（tilian / gengxin）沿用同一领域名。

## 何时用 / 何时不用

**用：**
- 要执行一个值得沉淀为案例的复杂任务，并希望把过程逐条留痕；
- 需要产出「可复用的执行流 / 指令表 / 方案」素材。

**不用：**
- 只是管理待办、排优先级、跟踪执行次数 → 用 `planing-biao`
- 长跑项目、需求反复修订、issue / 迭代 → 用 `chang-plan`
- 一次性、无需沉淀的动作

**边界表：**

| 需求 | 用哪个 |
|---|---|
| 小任务队列 / 每日任务 / 执行次数 | `planing-biao` |
| 长跑项目 / 需求 / issue / 迭代 | `chang-plan` |
| 把解决过程采集为案例、供提炼 | **本 skill** |

## 铁律（MUST）

1. **未确认任务边界，不得开始采集。** 确认来源：用户在当前会话明确确认，或任务描述本身已给出明确目标与边界。二者都无 → 停下询问，不得擅自扩大范围。
2. **每执行一条指令，先把结果写入执行流，再执行下一条。** 攒着写、事后补写 = 数据集污染，一律违规。失败/报错的指令同样必须记录。**用户纠正 agent 判断时，同样要当场记一个 `->` 块**（见「用户纠正」）。
3. **大步骤分化在案例创建时冻结**，之后只能标记「跳过」，不得增删或重排。
4. **`biao_xin.txt` 是生命周期的唯一权威**；采集真相在 `qingdan.txt` 与 `buzou/`。
5. **案例编号一旦分配，永不复用。**
6. **append-only 文件末尾必须始终保留一个 `★` 哨兵。**
7. **禁止本地模型参与本 skill（防污染）**：会话若在使用 Ollama / 本地 LLM，**不得进入或继续采集**；不得用本地模型生成、改写、补全任何 `->` 块、`qingdan`、`renwu` 或案例文件。本地模型只允许配 `zhishiku-chuli` + `ctf-pwn`；采集/提炼/回注必须由主 agent（非本地小模型）在**关闭本地模型写库模式**后执行。若当前是本地模型会话 → **立即停止本 skill，只报告「caiji 已禁用（本地模型模式）」**，不得写盘。

## 两级粒度（核心概念）

| 级别 | 含义 | 存哪 | 谁写 |
|---|---|---|---|
| **大步骤** | 案例拆分出的一个阶段，如「打开 qq」 | `qingdan.txt` 一行 + `buzou/NN.txt` 一个文件 | 低频：每开始一个大步骤 |
| **执行流** | 实现该大步骤的详细过程，细到具体指令 | 写在对应大步骤文件内部，竖排 `->` 块 | 高频：每执行一条指令 |

- 清单管**导航**（快速缩小到哪个大步骤），执行流管**采样**（具体每条指令与结果）。
- 两级都不许把另一级的粒度混进来：清单里**不得**出现单条指令，执行流里**不得**出现别的大步骤。

## 领域（分库）

一个领域 = 一个库 = 一个文件夹。领域名由用户定义（如 `ctf-pwn`、`web`、`python-env`）。

- 新建案例前**必须询问用户**本次属于哪个领域；先列出 `<数据根>/` 下已有领域供选，避免同一领域被写成多个名字。
- 领域记入 `renwu.txt` 的 `领域：` 字段，并决定案例放进哪个库。
- **领域一旦确定，不得中途更改**（改了等于换库）。
- 非交互且未指定领域 → 停下询问，不得臆断。

## 数据布局（按领域分库）

```text
<skill 目录>/xinxi.txt                     # 每个数据根两行：caiji_wei_win / caiji_wei_linux
<数据根>/<领域>/                            # 一个领域 = 一个库
  ├─ biao_xin.txt                          # 该领域的案例索引（order | id | flag，权威）
  ├─ biao/dai/<编号>/                      # 一个案例 = 一个文件夹
  │    ├─ renwu.txt                         # 案例信息 + 领域 + 冻结的大步骤分化
  │    ├─ qingdan.txt                       # 大步骤索引（末尾哨兵）
  │    └─ buzou/<NN>.txt                    # 各大步骤文件（末尾哨兵）
  └─ biao/hui/<编号>/                      # 已归档案例（结构同上）
```

- `<编号>` 在**领域内**自增；不同领域可以重号，互不影响。
- 案例的唯一标识是 `<领域>/<编号>`；下游溯源都用这个格式。

> 文件名保留 `renwu.txt` / `biao/dai` 等命名（历史兼容）；语义上它们分别承载「案例信息」与「待采集/已归档」。

## 格式规范

### xinxi.txt

```text
caiji_wei_win: <Windows 数据根绝对路径>
caiji_wei_linux: <Linux 数据根绝对路径>
```

每个数据根给两行：`<根名>_win` 与 `<根名>_linux`，指向**同一个文件夹**（Windows 与 Linux 双端共享同一份数据）。

**跨平台路径解析（MUST）**：读 `xinxi.txt` 后，按当前运行环境选路径——

- 运行在 **Windows** → 取 `<根名>_win`（形如 `C:/Users/xi/.pi/agent/skills/...`）。
- 运行在 **Linux**（含 WSL）→ 取 `<根名>_linux`（形如 `/media/xi/系统/Users/xi/.pi/agent/skills/...`）。
- 只存在单行旧格式 `<根名>: <路径>` → 按当前 OS 判断该路径是否可访问；可访问直接用，不可访问则询问用户另一平台的路径并补写成两行。

两行必须指向同一份数据根；若不一致 → 停下，让用户确认保留哪一个。

### biao_xin.txt

```text
# order | id | flag
[dai]
1|0001|0
2|0002|2

[hui]
1|0003|4
```

- 分隔符固定为 `|`，节标题固定为 `[dai]` / `[hui]`；分隔符不得出现在字段内。
- `order`：采集顺序，可手工调整（把某案例提前就改成 `1`，其余顺延）。
- `id`：4 位十进制、全局自增、永不复用；案例文件夹名 = `<id>`。
- `flag`：

| 含义 | 值 |
|---|---|
| 待采集 | 0 |
| 采集中 | 1 |
| 归档中（崩溃恢复标记） | 2 |
| 完成归档 | 4 |
| 无需用户确认即可交付 | 8 |

- 必要状态 ∈ {0, 1, 2, 4}，互斥且必选其一；`8` 是可选附加位：`flag = 必要状态 + 8`。
- 合法取值只有 `0 1 2 4 8 9 10 12`。出现其它值 = 数据损坏，停下询问用户。
- **`flag & 8` 时**，大步骤全部完成后可直接交付；否则必须等用户确认。

### renwu.txt（案例信息）

```text
---
案例：<一句话目标>
领域：<领域>
边界：<做什么、不做什么>
编号：<id>
题目：<题名/目标名，必填>
原路径：<原题/原目标目录的绝对路径；暂无则写 未知>
---
## 大步骤分化（创建时冻结）
1. <大步骤>
2. <大步骤>
```

- **`题目：`（MUST）**：可指认的对象名。CTF/题包写题名（如 `[LitCTF 2023]ezlogin`、`hardof`）；软件/目录任务写目标名（如 `qq`）。不得留空，不得用「一句话目标」代替（`案例：` 是目标描述，`题目：` 是溯源名）。
- **`原路径：`（MUST 有字段）**：原题包/原目标所在目录的**绝对路径**（跨平台时优先写当前 OS 能访问的那条，如 WSL 下 `/mnt/d/pwn/nss/案例/xiao_pwn`）。创建时已知 → 必须写绝对路径；当时确实不知道 → 写 `未知`，**不得省略该行**。
- 有多个相关路径时：`原路径：` 只记**原题主目录**（交付 exp/wp 的那层）；临时目录、libc 池、参考题路径写进执行流，不占本字段。
- **创建后默认不改写**。唯一例外：`原路径：` 仍为 `未知`、采集中已确认绝对路径时，允许**只把该字段从 `未知` 改成绝对路径一次**；已是非空绝对路径则不得再改。跳过的大步骤不改这里，只在对应大步骤文件里标注。

### qingdan.txt（大步骤索引，粗粒度）

```text
# 大步骤索引（写入位＝文末的哨兵行；一行一个大步骤）
# 文件 | 大概内容
buzou/01.txt | 打开 qq
buzou/02.txt | 打开音乐
★
```

- 每开始一个大步骤，就追加一行 `<文件路径> | <大概内容>`。
- 只追加，不改行、不删行。大步骤的完成 / 跳过状态写在它自己的文件头部，不占清单。
- ★ 上方最后一行 = 当前（最近开始的）大步骤。

### buzou/NN.txt（大步骤文件，细粒度）

```text
# 大步骤：打开 qq
# 编号：01
# 状态：进行中

执行流：
-> 搜索本地软件
   位置：终端
   指令：<完整命令>
   结果：未找到
   结论：本地没有 qq
-> 询问用户是否安装
   位置：终端
   指令：<交互>
   结果：用户确认安装
   结论：继续
★
```

- `NN` = 大步骤序号（对应冻结的分化）。
- 头部 `状态` ∈ `进行中 / 完成 / 跳过`。
- 每条指令一个 `->` 块，**竖排、独占多行、互不并排**；`->` 行写操作，其下固定四行：位置 / 指令 / 结果 / 结论。
- 只追加 `->` 块，不改写旧块。命令失败也照写，结果照抄原始输出，结论写实际判断。
- `位置` 通常写 `终端` / `浏览器` / `文件` / `知识库` 等；**用户纠正固定写 `用户纠正`**（见「用户纠正」）。

### ★ 哨兵写入位

所有 append-only 文件（`qingdan.txt`、每个 `buzou/NN.txt`）末尾始终保留一个独占一行的 `★`。

追加内容 = 一次替换，**不读全文**：

```text
Edit: oldText = "★"
      newText = "<新内容>\n★"
```

结果 = 新内容插在末尾，`★` 重新落在最后一行。

- `★` 必须独占一行、全文件唯一。
- **禁止**在描述、指令、结果等任何内容里出现 `★`，**表头/注释行也一样**——否则 `Edit oldText = "★"` 会歧义（可能改到注释里的那个），也直接破坏「全文件唯一」。
- `★` 缺失或重复 → 停下，读全文修复（这是唯一需要读全文的情况）。
- 头部信息（如 `状态`）不属于 append-only，可直接改写；`★` 不受影响。

## 协议

复制此清单并逐项勾选：

```text
- [ ] 1. 确认边界、领域、题目与原路径
- [ ] 2. 解析数据根
- [ ] 3. 新建案例
- [ ] 4. 采集大步骤与执行流
- [ ] 5. 交付归档
```

**1. 确认边界、领域、题目与原路径**
边界按顺序判定：

- 任务描述里已给出明确目标与边界（例如「只做 X，不要做 Y」）→ 视为**已确认**，直接进入第 3 步前仍须收齐题目/原路径。
- 否则与用户确认目标与边界（做什么、不做什么）。未确认不得进入第 3 步。
- 非交互执行（一次性 / 无用户可回复）且边界不明确 → **停下并说明缺哪项边界**，既不要空转，也不要擅自扩大范围。

领域：

- **必须询问用户**本次案例属于哪个领域；先列出 `<数据根>/` 下已有领域供选。
- 非交互且未指定领域 → 停下询问，不得臆断。

题目与原路径（溯源，MUST）：

- **`题目：`**：从用户描述、题包目录名或二进制名提取；仍不明确 → **询问用户**，不得用空泛词（如「本题」「pwn题」）凑数。
- **`原路径：`**：优先问/查原题目录绝对路径。用户已给路径、或工作区就是题包目录 → 写成绝对路径。确实拿不到 → 写 `未知`，但 `题目：` 仍必须有可指认名称。
- 最低标准：**至少记下题目名**；有路径时路径优先于「以后再找」。

> 只要边界/领域/题目不是「明确给出」，就必须先问。未确认不得写盘。`原路径：未知` 可以开工，但不得缺 `题目：` 行。

**2. 解析数据根**
读 `<skill 目录>/xinxi.txt`，按上面「跨平台路径解析」规则选出**当前 OS 对应**的 `<数据根>`：

- 有可访问的路径 → 视需要读 `<数据根>/<领域>/biao_xin.txt`。
- 文件缺失、为空、或当前 OS 对应的路径不存在 → 询问用户是否在默认位置（`<skill 目录>/caiji_wei/`）初始化；确认后创建完整目录结构，把 Windows 与 Linux 两条路径都写入 `xinxi.txt`，再继续。

**3. 新建案例（写入对应领域库）**
1. 在 `<数据根>/<领域>/` 下分配新 `id`（该领域内现有最大 id + 1）。
2. 创建 `<数据根>/<领域>/biao/dai/<id>/`、`buzou/` 子目录。
3. 写 `renwu.txt`（含 `领域：`、`题目：`、`原路径：`），把大步骤分化冻结进去；**不预建** `buzou/` 文件。缺 `题目：` 或整行 `原路径：` → 不得创建。
4. 写 `qingdan.txt` 骨架（表头 + 一个 `★`）。
5. 在 `<数据根>/<领域>/biao_xin.txt` 的 `[dai]` 追加一行，`flag=0`。

> 先写文件夹、后写索引：中途崩溃最多留下一个未入索引的孤儿文件夹，下次启动扫描 `dai/` 即可补回。

**4. 采集大步骤与执行流**
1. 取案例时先把索引中该行 `flag` 从 `0` 改为 `1`（采集中）——最早一次强制落盘。
2. 按大步骤顺序推进。**开始一个大步骤时**：创建 `buzou/NN.txt`（含头部、空执行流、末尾 `★`），并向 `qingdan.txt` 哨兵处追加一行。
3. 在该大步骤内**逐条执行指令**，严格遵守「采集节奏」：执行一条 → 用哨兵追加一个 `->` 块 → 再执行下一条。
4. 大步骤完成 → 把该文件头部 `状态` 改为「完成」；跳过则改为「跳过」并注明。
5. 用户否认结果 → 回到当前大步骤继续。
6. 若 `renwu.txt` 的 `原路径：` 仍为 `未知`，而执行中已 `cd`/确认原题绝对路径 → **立刻**把该字段补成绝对路径（仅此一次），再继续采集。

> 一次回复里若执行了 3 条命令，就必须产生 3 次 `->` 块追加。追加次数少于执行条数 = 违规。

**5. 交付归档**
所有大步骤完成后：先检查 `renwu.txt` 仍有非空 `题目：`，且存在 `原路径：` 行（绝对路径或 `未知`）。缺字段 → 补全后再交付。若 `flag & 8`，直接交付；否则请用户确认交付。确认后按顺序执行：

1. 索引中该行 `flag` 改为 `2`（归档中）。
2. 案例文件夹从 `biao/dai/<id>/` 移到 `biao/hui/<id>/`。
3. 索引行从 `[dai]` 移到 `[hui]`，`flag` 改为 `4`，`order` 重排。

> `flag=2` 是崩溃恢复标记：启动时若发现 `flag=2` 的行，按上面步骤 2–3 继续收尾。

## 采集节奏（一条指令一次写）

**一条指令 = 一次命令 / 一次工具调用 / 一次用户交互。**

```text
执行一条指令 -> 用哨兵追加一个 -> 块 -> 才允许执行下一条
```

哨兵让这次写入变成「一次替换」，**不用读全文、不与文件长度相关**，所以没有攒着写的技术理由。

- **禁止**：连续执行两条指令而中间没有追加。
- **禁止**：在回复里陈述尚未写入执行流的结果。
- **禁止**：预先批量创建 `buzou/` 文件，或结尾一次性补齐多个 `->` 块。

### 为什么必须逐条写（数据质量，不是洁癖）

每个 `->` 块是**一条采集样本**。

- 事后补写的「结果」是**回忆或总结**，不是原始输出；用它提炼出的「常用指令表」是二手誊抄。
- 攒写会切断「指令 ↔ 真实输出」的对应关系：哪条命令产出了哪段输出，事后无法还原。
- **失败和报错的步骤是最有价值的知识点**（它们定义了坑在哪）；跳过后数据集就只剩成功路径，无法提炼排错方案。

**所以攒写不是「记录慢一点」，是「样本报废」。**

### 中断 ≠ 污染（必须分清）

这两件事经常被混为一谈，但处理方式完全相反：

| | 中断 | 污染 |
|---|---|---|
| 是什么 | 会话/进程结束，最后一条指令未落盘 | 「结果」是回忆、总结或改写出来的，不是原始输出 |
| 数据状态 | **缺口**（少了一条记录） | **失实**（记录存在但内容假） |
| 怎么办 | **可恢复**：下次启动自检，以 `buzou/` 与 `qingdan.txt` 为准，从最后一个已落盘的 `->` 块之后继续 | **不可恢复**：该样本报废，需重新执行并重采 |
| 能否继续用 | 能。缺口位置明确，其余样本仍然有效 | 不能。真假难辨，会污染后续提炼 |

判定标准只有一条：**这条「结果」是不是当时的原始输出？**

- 是 → 有效，哪怕数据不完整（有缺口）。
- 不是（是事后想出来的）→ 污染。

**断网、超时、用户叫停、上下文被清，都只是中断，不是污染。** 不得因为一次中断就判定整份案例作废、更不得删除已有样本。

### 为什么会想攒着写（必须识破的借口）

| 借口 | 现实 |
|---|---|
| 指令太琐碎，不值得写 | 琐碎指令正是常用指令表的候选；攒着写 = 采样空缺 |
| 结果还没稳定，等确定了再写 | 先写已发生的原始输出，结论标「待定」；写入不应被结论阻塞 |
| 这条报错了/没产出，不用记 | 失败路径是最值钱的知识点；跳过 = 数据集失真 |
| 先跑完，最后统一整理成案例 | 「整理」= 用总结替换原始输出，样本报废 |
| 哨兵写入也麻烦，最后一起写 | 哨兵就是为省事设计的：一次替换，不读全文 |
| 先回复用户结果，回头再补写 | 先写回再回复；回复不是采集 |
| 写文件会打断思路 | 思路不可恢复，采集可以 |

### 红旗（出现任意一条，立即停下补写）

- 我打算「先跑完，再统一整理成案例」。
- 我在用总结/转述代替原始输出。
- 我把失败或报错的步骤跳过了没记。
- 我的回复里出现了尚未写入执行流的结果。
- 我准备在结尾一次性追加多个 `->` 块。
- 我预先创建了多个 `buzou/` 文件。
- 我连续执行了两条指令，中间没有追加。
- 我跳过了 `flag` 从 0 到 1 的更新。
- **当前是本地模型会话，却仍在采集或让 Ollama 写 `->` 块 / 案例文件。**
- 用户纠正了我，我嘴上改了，却没当场记 `->` 块。
- 我把用户的原话转述成了自己的话（`结果` 不是原话）。
- 我把偏好类纠正（格式 / 语气）也当成知识样本记了块。

## 用户纠正（第三类采样点）

前两类采样点是「指令 ↔ 原始输出」和「失败」。第三类是**用户纠正 agent 的判断**——它比失败更值钱：

- 失败说明「这么做不行」；
- 纠正说明「**agent 当时的想法就是错的**」。

这是唯一能直接采到「agent 会犯什么错」的渠道，下游可用来生成「合理化表」和「铁律」。

### 触发条件（任意一条）

- 用户说「不对 / 不是这样 / 应该……」并给出不同做法；
- 用户推翻 agent 的结论、方案、判断或边界；
- agent 自己发现按用户上一条说法理解错了并改口。

**纯格式 / 语气 / 语言偏好不算**（如「用中文」「别加表格」）：那是偏好，不是知识，不建块。

### 动作：当场追加一个 `->` 块，`位置` 固定写 `用户纠正`

```text
-> 用户纠正：<被纠正的判断（一句话）>
   位置：用户纠正
   指令：<agent 原做法 / 原判断，写具体>
   结果：用户答复：<用户原话，照抄>
   结论：<修正后的做法>
```

- **`指令` 写 agent 当时到底做了什么、认为什么**，不要写成「我理解错了」这种没有信息量的自述。
- **`结果` 照抄用户原话**。转述会把「用户到底反对哪一点」洗掉——这和用总结代替原始输出是同一类污染。
- **`结论` 写修正后的做法**，供下游提炼成规则。
- 一次纠正 = 一个块。用户连纠三次 = 三个块，**不要合并**成「用户多次纠正」。
- 仍然遵守采集节奏：纠正发生 → 先写块 → 再继续下一步。

> 用户纠正属于「**已发生的事实**」，不是中断，也不是可以省略的寒暄。漏记一个纠正 = 数据集里少了一条最值钱的样本。

## 启动自检

每次开始工作前，**按领域库逐个**校验磁盘一致，发现偏差先修复再执行：

- `<数据根>/<领域>/` 下结构不符（缺 `biao_xin.txt` 或 `biao/`）→ 停下询问用户。
- 案例 `renwu.txt` 的 `领域：` 与所在领域文件夹不一致 → 以所在文件夹为准，修正字段。
- 案例 `renwu.txt` 缺 `题目：` 或缺 `原路径：` 行 → 能从执行流/用户消息还原则补上；否则标缺口并询问用户（`题目：` 至少要有可指认名；路径实在没有就写 `原路径：未知`）。旧案例无这两行时，**不强制回填才能继续读**，但**新采集/新归档必须有**。

- `[dai]` 中有 `flag=2` 的行 → 续做归档步骤 2–3。
- `dai/` 存在索引里没有的案例文件夹 → 补进 `[dai]`，`flag=0`。
- `qingdan.txt` 有行、但 `buzou/` 缺对应文件 → 以 `qingdan.txt` 为准，停下询问用户（文件丢失）。
- `buzou/` 有文件、但 `qingdan.txt` 缺对应行 → 以 `buzou/` 为准，补行到哨兵处。
- `buzou/NN.txt` 头部状态与实际执行流不符 → 以执行流为准修正头部。
- `->` 块里出现总结性描述、缺少原始输出 → 标记为可疑样本，请用户确认是否补采。
- 执行流在某处中断、后续缺失 → 这是**缺口不是污染**：能重现就补采，不能重现就标注「未采集」并继续，**不得删除已有样本**。
- append-only 文件缺 `★` 或 `★` 不唯一 → 读全文修复。

## 示例

案例：打开 qq 后，打开音乐。进行到「打开 qq」的第 2 条指令后。

**renwu.txt**
```text
---
案例：打开qq后，打开音乐
领域：desktop-app
边界：本地，不执行其他操作
编号：0001
题目：qq
原路径：未知
---
## 大步骤分化（创建时冻结）
1. 打开 qq
2. 打开音乐
```

（CTF 例：`题目：[LitCTF 2023]ezlogin`，`原路径：/mnt/d/pwn/nss/待完成/[LitCTF 2023]ezlogin`）

**qingdan.txt**（已开始大步骤 1）
```text
# 大步骤索引（写入位＝文末的哨兵行；一行一个大步骤）
# 文件 | 大概内容
buzou/01.txt | 打开 qq
★
```

**buzou/01.txt**
```text
# 大步骤：打开 qq
# 编号：01
# 状态：进行中

执行流：
-> 搜索本地软件
   位置：终端
   指令：<搜索命令>
   结果：未找到
   结论：本地没有 qq，需安装
-> 询问用户是否安装
   位置：终端
   指令：询问是否安装 qq
   结果：用户确认安装
   结论：进入安装
★
```

执行第 3 条指令（查找安装包并安装）后，**只做一次替换**：

```text
Edit: oldText = "★"
      newText = "-> 查找安装包并安装\n   位置：浏览器\n   指令：<站点>\n   结果：下载并安装成功\n   结论：可启动\n★"
```

**失败样本也要照记**（示意）：
```text
-> 启动 qq
   位置：终端
   指令：qq
   结果：command not found
   结论：安装未写 PATH，需用绝对路径
```

**用户纠正样本也要照记**（示意）：
```text
-> 用户纠正：以为要先装 QQ 才能看音乐
   位置：用户纠正
   指令：agent 判断「本地没有 qq，需先安装再继续」
   结果：用户答复：不用装 qq，音乐是网页版，直接开浏览器就行
   结论：QQ 与音乐无关，不要臆断依赖顺序；先问清各步骤的依赖
```

## 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 用总结代替原始输出 | 采样污染，指令表失真 | 照抄真实 stdout / 报错 |
| 跳过失败或报错的步骤 | 丢掉最有价值的知识点 | 失败路径必须记 |
| 攒着写 / 结尾一次性整理 | 数据集报废 | 一条指令一次追加 |
| 未确认边界就采集 | 范围失控、采集跑偏 | 先确认，或描述已明确 |
| 清单里写单条指令 | 层级混淆、清单失去导航作用 | 清单只放**大步骤** |
| 执行流里写别的大步骤 | 层级混淆 | 一个文件只装一个大步骤 |
| 用回复代替采集 | 结果只在对话里，清上下文即丢 | 先写回文件，再回复 |
| 创建后修改大步骤分化 | 采样点与进度错位 | 只能标记「跳过」 |
| 预先批量建 `buzou/` 文件 | 出现空壳大步骤文件 | 开始时才创建 |
| append-only 文件丢了 `★` | 无法定位写入点 | 读全文修复并补回 `★` |
| 归档只改索引、不移动文件夹 | 索引与磁盘漂移 | 严格按 2→3→4 顺序 |
| id 复用或重号 | 归档覆盖旧案例 | id 在领域内永不复用 |
| 跨领域混放 / 领域中途更改 | 库失去意义、溯源错乱 | 一个领域一个库，定了不改 |
| 不写 `题目：` / 省略 `原路径：` | 事后找不到原题包，案例无法溯源 | 至少题名；有则写绝对路径，无则 `未知` |
| 把临时目录、libc 池写进 `原路径：` | 溯源指错交付目录 | `原路径：` 只记原题主目录 |
| 用户纠正只改做法、不记样本 | 丢掉最值钱的「agent 会怎么错」证据 | 当场记 `位置：用户纠正` 的 `->` 块 |
| 纠正块的 `结果` 是转述而非原话 | 「用户到底反对哪一点」被洗掉 | 照抄用户原话 |
| 把偏好类纠正记成知识样本 | 知识库混入个人口味，无法复用 | 只有知识性纠正才建块 |
