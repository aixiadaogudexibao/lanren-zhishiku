# 知识库处理层（zhishiku-chuli）

## 概述

本 skill 是知识库系统的**处理层**（入口 / 编排器）。

前面三个（`zhishiku-caiji` / `zhishiku-tilian` / `zhishiku-gengxin`）构成**知识库层**；本 skill 用知识库层的产物去处理用户请求，并在遇到**未记录情况**时反哺知识库，形成闭环。

## 详细规范索引（references/）

本文件只留主干与判断要点；细则在下列文件，**按需 read**：

| 文件 | 什么时候要读 |
|---|---|
| `references/xinxi-geshi.md` | 要新建/修改缺口板任务节、写明细字段、判定维护时机 |
| `references/fanzheng-biao.md` | 要打标前做反证；或本轮用过 wp 需过专项判定表 |
| `references/wp-caiji.md` | 要判断「有 wp 是否还需采集」 |
| `references/caiji-liucheng.md` | 要开 caiji 时的完整 9 条流程 |

规则：**不预先读**。主线走到哪一步，再 read 对应文件。

## 触发词与模式

| 说法 | 含义 |
|---|---|
| **使用知识库系统** | 单次：用知识库处理**这一个**请求 |
| **开启知识库系统模式** | 持续：**所有任务**都用知识库系统处理，直到用户说「关闭知识库系统模式」 |
| 关闭知识库系统模式 / 退出知识库系统 | 恢复正常处理（不再强制走知识库） |

- 听到「使用知识库系统」→ 对**当前这一个**请求走本 skill 的处理流程。
- 听到「开启知识库系统模式」→ 进入持续模式：**之后每个用户任务**都先走本 skill（查领域知识 → 未记录先打标做完 → **完成后**按标记调 caiji → 自动回注）。
- 模式是**会话级**的：新会话默认关闭，需用户重新开启。
- 模式开启期间，不得绕过本 skill 直接用通用能力处理任务。

### 缺口板 `xinxi.txt`

路径：`<本 skill 目录>/xinxi.txt`（Linux 默认 `~/.pi/agent/skills/zhishiku-chuli/xinxi.txt`）

**用途**：本轮任务有无知识缺口、`caiji标记` 是 0 还是 1 的**磁盘真相**。压缩/岔话题/重载后以它为准。

- 判定采不采 → 先读当前任务节的 `caiji标记`；续跑条里的「采集标记」只是摘要，冲突以本文件为准。
- 打标 = **写本文件**，不是只在回复里说一句。
- 节格式、明细字段（层/类型码/反证/差在）、维护时机 → 见 `references/xinxi-geshi.md`

### 续跑条 `resume/current.md`

路径：`<数据根>/resume/current.md`（Linux 默认 `~/.zhishiku/resume/current.md`；Windows 同源 `%USERPROFILE%\.zhishiku\resume\current.md`）

**用途**：记录链阶段 C0–C5/闭、题目、下次动作，供压缩/重载/多窗口后接着做。

- 判定阶段 → 读它；**磁盘真相 > 聊天记忆**。
- **多窗口共写**：禁止 write 整文件覆盖，一律走 `scripts/resume_lock.py`（commit / patch / note / takeover / beat）。
- 完整字段、心跳规则、冲突处理 → 见 `~/.pi/agent/AGENTS.md` 的「续跑条」节。

## 处理协议

```text
- [ ] 1. 确定领域
- [ ] 1.5 外部线索（公开 writeup / 相关信息）——**CTF/pwn 等可指认赛题：载入知识与深挖前 MUST 先做**；wp 只是加速选枝，**不是免采集票**（见「WP 与采集的关系」）
- [ ] 2. 载入领域知识（总览 + 按需卡片，勿整目录塞进上下文）
- [ ] 3. 拆解用户请求为大步骤（可吸收 1.5 线索）
- [ ] 4. 逐步处理（分诊 → 树选枝 / 并列择一 → 打开当前卡片 / 指令表 / 错误处理）
- [ ] 5. 遇候选未记录 → **先反证（读过/对不上/选错分叉/近似）** → 通过则写入 `xinxi.txt`（caiji标记：1 + 层/类型码/反证/差在/…），继续做完（此时不调用 caiji）。**用过 wp 的必须按「WP 专项判定」表落地；wp 复现成功而库无卡 → 必须标 1**
- [ ] 6. 任务完成后分支（**先读 `xinxi.txt` 该任务 `caiji标记`**）：
        · `caiji标记：0` → **直接把结果交给用户**（不 caiji / 不 tilian / 不 gengxin）；节改闭/`当前：无`
        · `caiji标记：1` → 先保证用户侧结果已交付（节：已交付待采），再 caiji → tilian → gengxin；采后清标记
- [ ] 7. 收尾记账（实战使用 + 生命周期；不挡交付）
- [ ] 8. IoT 领域 → 样本交接 ai_iot（见下「IoT 样本交接」）
- [ ] 9. 报告（有标记时写采集/回注情况；无标记时报告从简；1.5 线索来源一句）
- [ ] 10. 交付物：在原题目目录留下 exp_agent.py 与 wp_agent.md（仅 pwn/CTF；勿覆盖用户 exp.py/wp.md）
```

**1. 确定领域**：判断请求属于哪个领域，匹配已有领域库；无匹配就问用户。

**1.5 外部线索：公开 writeup / 相关信息（最先触发之一）**

目的：在 dig 二进制、堆布局、盲 ROP 之前，先用**可公开检索**的 writeup/exp 笔记把「漏洞形态 + 关键偏移/地址/技巧」摸清，避免长时间卡在已知公开题的弯路上。本步是**线索**，不是替库、不是交卷抄袭源。

### 何时 MUST / 何时跳过

| 情形 | 动作 |
|---|---|
| 领域为 **`ctf-pwn`** / 明确是 CTF·HTB·竞赛二进制·Web 题，且题名/赛事可指认 | **MUST 先做**（在步骤 2 深载与步骤 4 深挖前） |
| 用户明示「先搜 wp / 找 writeup / 对照公开题解」 | **MUST 先做**（任何领域） |
| 处理中已卡死 ≥1 条主路径、库内卡用尽 | **补做**（不必等下次） |
| 领域为装环境/改配置/私有业务脚本等**无可检索赛题名** | **跳过**（报告可不提） |
| 无网 / 检索全空 / 只有无关同名题 | **记失败原因 → 立刻回退步骤 2**，禁止空等 |

### 怎么搜（短、可复现）

1. **关键词**（由宽到窄，至少两轮）：
   - `<平台/赛事> <题名> writeup`（如 `HTB abyss pwn writeup`、`Business CTF 2024 abyss`）
   - `<题名> pwn exploit` / `site:github.com <题名>` / 官方 `hackthebox/business-ctf-*` 树
2. **入口**（有网时；工具以本机为准）：
   - `curl` 检索页（DuckDuckGo html / 可访问的搜索）→ 抽出候选 URL
   - 优先打开：**个人博客 writeup**、**GitHub exp/README**、**赛事官方题解树**；少依赖登录墙
   - 领域若有 `tools/wp-search.txt` → **按该规范**；无则用本段
3. **读的时候只捞线索**（写入续跑条或题目录草稿，勿整篇粘进知识库）：
   - 漏洞一句话（哪段 copy/哪次 read）
   - 关键技巧（如 `i` 劫持、部分覆写、跳进 `jne` 中段）
   - 数字：offset、gadget、目标地址（如 `user[17]=0x1c`、`ret→0x4014ed`）
   - 利用骨架：几发 payload、是否要 leak、最终读 flag 还是 shell
4. **禁止**：
   - 不核对本机 binary/源码就整份抄 exp 交卷
   - 把外站全文写进 `gengxin_wei` / caiji `结果`（caiji 只记**你复现跑通**的命令与输出）
   - 因「已经有 wp」跳过步骤 2 载库与反证（**库仍要走**；wp 只加速选枝）
   - **因「已经有 wp / wp 已能做通」跳过步骤 5 打标与收尾查缺口**（见下「WP 与采集的关系」）
   - 无网时假装搜过；失败必须写明 `外部线索：无/失败：…`

### WP 与采集（摘要）

**wp 只是加速选枝，不是免采集票。** 依据 wp 复现成功而库内无对应卡时，这份「wp → 本机复现」正是最值得沉淀的缺口。

- 用过 wp（不论成败）→ 收尾必须回答「本轮有 wp，缺口已查：有/无」。
- wp 复现成功、库无卡 → **必须** `caiji标记：1`（层 `卡片`）或 `参数`。
- 完整六种情形判定表 → 见 `references/wp-caiji.md`

### 与后续步骤的衔接

- 有可用线索 → 步骤 3 拆解时**写进大步骤**；步骤 4 用库内卡**验证**偏移与保护（checksec/反汇编/本地复现）。
- 线索与本机不符（改保护、改 libc、去符号）→ 以本机为准，wp 当思路；可打标 `P-参数/布局` 若库缺「对照公开题需重核」类说明。
- 仅靠 wp 做通、库无对应卡 → 仍按步骤 5 反证打标，完成后 caiji（采的是**你的复现**，不是网页正文）。**这条不是可选。**

## 4 逐步处理

每步按顺序查：

- **执行流（目的优先 · 旧树兼容）**：
  1. 阶段门控（`menkan/workflow.xml` 的 `<pipeline>`）：先核对当前阶段信息是否已齐；未齐则补齐，**不改树、不替树选枝**。
  2. **选技术**：
     - **有 `diaoyong_mudi.txt` / `jishu/`**：R 填标签 → 缺口目的 → mudi/silu → jishu（Min 匹配）；清单 `jineng_mudi.txt`。多目的按 silu 串联（如 `silu.chain.rexp_like`）；**禁止**要求旧 H.rexp/H.policy 整树条件一次性全真才开工。
     - **无 mudi（非 ctf-pwn 等）**：该领域 `diaoyong.txt` / `liucheng.txt`。
     - **ctf-pwn**：不得把 `archive_jiu_shu/diaoyong.txt` 当路由；无 jishu 命中 → 打标，不用旧长∧否决。
  3. **走流程**：优先 `jishu/<目的>/<ID>.md` + 别名到旧卡细步骤；无 jishu 则 `liucheng/shu/<标号>.md` → `liucheng_biao`。可只走一段。
  4. **多节点同时满足（并列候选）**：分叉旁写着 `候选：A | B | C`（或卡片有 `## 并列`）且条件同时命中多个时，**不得随手挑**；跑
     ```
     python3 <skill 目录>/zhishiku-gengxin/scripts/yongfa.py <数据根>/<领域> --pick <键1,键2,...>
     ```

## 启动自检

处理前：

- 领域库存在，且 `liucheng.txt` / `cuowu.txt` / `zhiling.txt` 至少有一个非空。
- **CTF/pwn 可指认题**：已做步骤 1.5（有线索摘要或明确 `外部线索：无/失败：…`）；有 `tools/wp-search.txt` 则已按需读。
- 若 `liucheng.txt` 为树形总览：确认读法/分诊可读；需要执行时能打开对应 `liucheng_biao/<标号>.txt`。
- 引用的知识条目能对上（`来源` 可读）。

处理前（另）：

- 已 read 本 skill `xinxi.txt`；若有未闭且 `caiji标记：1` 的旧任务节，先按续跑/用户意图决定续采还是新开节，**禁止**静默丢旧标记。

处理中遇缺口时：

- 已写入本 skill `xinxi.txt`：该任务节存在且 **`caiji标记：1`**，明细含层/类型码/何时/反证/差在/当时判断（越过后补如何越过）；不得只放在嘴上。
- 已扫描其他 skill；选中的 skill 已读并遵循；越过缺口后已回到主流程。
- **未**在处理中途打开 caiji。

任务完成后：

- **用户侧结果已交付**（答案/产物/结论可见）。
- **pwn/CTF 题：交付物双份已落盘**（这是最容易漏的一项，必须逐条核）：
  - `exp_agent.py` 已在原题目目录，且**实际跑通过**（拿到 shell 或读到 flag）；
  - **`wp_agent.md` 已在同一目录**——没跑通也要写（记录卡在哪、下一步思路）；
  - 检查方式：`ls <原题目目录>/exp_agent.py <原题目目录>/wp_agent.md`，**两个都得存在**；
  - 只有 exp 没 wp = **交付未完成**，不得报“已交付”；
  - 不碰用户的 `exp.py` / `wp.md`。
- 已 **read `xinxi.txt`** 再分支。
- `caiji标记：0` → 已**复查**缺口（用过 wp 的能说出「缺口已查：无」+ 覆盖卡号）；确认未调用 caiji/tilian/gengxin；未用库务挡住交付；节已闭/`当前：无`。
- 本轮**用过 wp**（不论成/败）→ 已显式回答「本轮有 wp，缺口已查：有/无」；**未因有 wp 跳过步骤 5 或收尾查缺口**。
- `caiji标记：1` → 交付之后 `zhishiku-caiji` 已按 **`xinxi` 明细**复现采集；不可用 → 在已交付前提下报告「有标记未采集」，**保留**文件中的 1 与明细。
- 若已采集，确认缺口已进入 `gengxin_wei/<领域>/`（tilian→gengxin 完成）或已说明待回注；并已把该任务 `caiji标记` 清 0 或节闭。
- 收尾已跑过 `yongfa.py --tick`（含空轮次，且**不挡交付**）；或已明确注明「未记账（本地模型模式）」。
- 已跑 `scripts/show_flow.py`，并在交付报告里给出**本轮技术卡 + `->` 执行流**（无卡则明写「本轮未用技术卡」）。
- 若输出提到「生命周期归零」：已汇总询问用户，并按答复执行了 `--expire` / `--refresh`（无答复则停在 `待裁决`）。

## 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 遇到缺口不写 `xinxi.txt` | 完成后无 caiji，知识库永不增长 | 反证通过 → 该任务 `caiji标记：1` + 层/类型码/反证/差在明细 |
| 明细无层/无反证 | caiji 只能整段采、易误标 | 方案 A 字段写全；参数层与路由层分开 |
| 只在聊天打标、不落 `xinxi` | 压缩后标记丢失 | 打标=写本 skill `xinxi.txt` |
| 处理中途就开 caiji | 打断主任务、边界混乱 | 做完再按 `xinxi` 采 |
| `caiji标记：1` 完成后不采 | 缺口永远在 | 有 1 → 必须 caiji |
| `caiji标记：0` 却开 caiji | 空案例 / 重复采已有知识 | 0 不采，直接交用户结果 |
| 标记 0 仍先写长库务再给用户 | 用户等结果，体验差 | 0 → 直接提交结果 |
| 标记 1 先采库再交结果 | 用户被采集卡住 | 先交付，再 caiji |
| 完成后总结填库、不复现 | 采样污染 | 按已通思路复现，照抄 stdout；标记来自 `xinxi` 明细 |
| 直接改知识库 | 绕过 gengxin 的安全规则 | 回注交给 gengxin |
| 领域猜错 | 用错库、知识进错地方 | 不确定就问用户 |
| 采集时攒着写 | 数据失真 | 遵守 caiji 的采集节奏 |
| 缺口处放弃任务 | 任务失败 | 打标 + 扫 skill / 通用能力继续做完 |
| 缺口不扫 skill、直接硬解 | 重复造轮子、标记质量差 | 先扫所有 skill，优先求助匹配的 |
| 求助其他 skill 后不返回主流程 | 脱离知识库系统 | 越过缺口后必须回到 chuli |
| 臆造知识库没有的知识 | 知识失真 | 只用库里有的；缺口靠标记+完成后采集补 |
| 用户纠正了判断却不打标不采 | 最值钱的纠错样本丢失 | 知识性纠正打标；完成后 caiji 记 `用户纠正` 块 |
| 用知识却不跑 `--tick` | 实战统计与生命周期都不动 | 收尾必须记账 |
| 收尾不给技术卡/执行流 | 不知道这轮到底走了哪条路 | 跑 `show_flow.py` 并写进报告 |
| 只写 `exp_agent.py`、没写 `wp_agent.md` 就报交付 | 下次回来看不懂当时怎么打的，知识也没沉淀 | 两份都写；没跑通也要写 wp 记录卡点 |
| `wp_agent.md` 写到知识库/别处而不是原题目目录 | 真题录里找不到，等于没写 | 固定写原题目父目录 |
| 有 wp 就直接标记 0 / 跳过采集 | 依据 wp 复现的新路永远进不了库，下次又得重搜 | wp 只是加速选枝；库无卡就必须标 1 |
| 收尾不复查 `xinxi.txt`，拿开场的旧印象判有无缺口 | 中途打的标被漏掉，链断在 C0 | 交付前再读一次当前任务节 |
| 凭题目顺序自己编 `->` 链 | 链是编的，下次没法复现 | 只连卡片里写明的「下一跳」 |
| 空轮次跳过记账 | 生命周期不倒计时 | 没用到知识也要跑 `--tick` |
| 手改 `yongfa.txt` / `shengming.txt` | 哨兵或状态被改坏 | 只经由 `yongfa.py` |
| 生命周期归零却自作主张 | 越权替用户决定 | 汇总成一次问；没答复停在 `待裁决` |
| 本地模型参与 caiji/tilian/gengxin | 案例与容器被胡写污染 | 本地模型仅 chuli+ctf-pwn；写库须关本地模型后由主 agent 走原链路 |
| 本地模型把输出写入 gengxin_wei/caiji_wei | skill/知识库被污染 | 本地模型只许读 ctf-pwn 库；落盘仅题目目录 |
| 多节点同时满足却随口挑一个 | 选枝不可复现 | 条件过滤 → `yongfa.py --pick` |
| 改了 `menkan/` | 门控失真 | `menkan/` 只读；由 gengxin 按用户确认写 |
| CTF 可指认题跳过 1.5 盲挖 | 公开题空转、重复踩坑 | 深挖前先搜 wp；失败写明再回退载库 |
| 有 wp 不复核就抄 / 网页进库 | 交付不可复现、库污染 | 本机验证；caiji 只采自己的复现输出 |
