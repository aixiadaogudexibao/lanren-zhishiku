# 知识库处理层（zhishiku-chuli）

## 概述

本 skill 是知识库系统的**处理层**（入口 / 编排器）。

前面三个（`zhishiku-caiji` / `zhishiku-tilian` / `zhishiku-gengxin`）构成**知识库层**；本 skill 用知识库层的产物去处理用户请求，并在遇到**未记录情况**时反哺知识库，形成闭环。

## 触发词与模式

| 说法 | 含义 |
|---|---|
| **使用知识库系统** | 单次：用知识库处理**这一个**请求 |
| **开启知识库系统模式** | 持续：**所有任务**都用知识库系统处理，直到用户说「关闭知识库系统模式」 |
| 关闭知识库系统模式 / 退出知识库系统 | 恢复正常处理（不再强制走知识库） |

- 听到「使用知识库系统」→ 对**当前这一个**请求走本 skill 的处理流程。
- 听到「开启知识库系统模式」→ 进入持续模式：**之后每个用户任务**都先走本 skill（查领域知识 → 未记录先打标做完 → **完成后**按标记调 caiji → 自动回注）。
- 模式是**会话级**的：新会话默认关闭，需用户重新开启。
- 模式开启期间，不得绕过本 skill 直接用通用能力处理任务。

## 系统全貌（四层）

```text
知识库层：  zhishiku-caiji（采集） ─▶ zhishiku-tilian（提炼） ─▶ zhishiku-gengxin（容器）
                                                                        │
                                                              读知识    │    ▲ 回注
                                                                        ▼    │
处理层：                        zhishiku-chuli（处理用户请求） ───────────────┘
                                          │
                                          └─ 未记录 → 打标继续 ─▶ 任务完成 ─▶ 有标记则 caiji ─▶ tilian ─▶ gengxin
                                                               （完成后采集并更新知识库）
```

|---|---|

| 长跑项目 / 需求 / issue / 迭代 | `chang-plan` |
| 采集执行过程 | `zhishiku-caiji` |
| 把案例提炼成知识 | `zhishiku-tilian` |

| **用知识库处理某领域的用户任务** | **本 skill** |

## 输入

- **用户请求**：某领域的一个任务。
- **领域知识库**：`gengxin_wei/<领域>/`
  - `liucheng/` 执行流**两层结构**：
    - `liucheng/diaoyong.txt` **调用树**（接题探针 + 路由：按题面选技术/选路径；怎么选）
    - `liucheng/jineng.txt` **技术树清单**（有哪些技术、入口、复用）
    - `liucheng/shu/<标号>.md` **技术树本体**（一技术的完整流程；可部分调用）
  - `liucheng.txt` 全标号索引（旧领域可能仍是单文件树；validate 依赖，保留）
  - `menkan/`（如 `menkan/workflow.xml`）**可选粗门控**（阶段 checklist / 已确认的判定点；无具体步骤；可空）。细枝选技术仍以 `diaoyong` 为准；缺 `<source>`/`<confirm>` 的 menkan → 只作参考，不当硬门槛（见领域 `menkan/README.txt`）
  - `liucheng_biao/<标号>.txt` 执行流**卡片**（时机/条件/做法/下一跳；怎么做）
  - `cuowu.txt` 错误处理（会怎么错、怎么修）
  - `zhiling.txt` 命令速查（具体指令）
  - `tieuli.txt` / `yuanze.txt` / `bianjie.txt`（铁律 / 原则 / 边界）
  - `tools/<工具名>.txt` 领域专用工具使用规范（如 `tools/libcsearch.txt`）
  - `yongfa.txt` 实战使用日志（**只读**；收尾时由本 skill 追加，见「7 收尾记账」）
  - `shengming.txt` 条目生命周期表（**只读**；收尾时由本 skill 维护，见「7 收尾记账」）
  - `liucheng_jiu_shupai.txt` 若存在：旧竖排备份，**仅**当总览指向「尚未卡片化」时按需翻阅

知识库根来源：读 `zhishiku-gengxin/xinxi.txt`（键 `gengxin_wei`）。该文件含两行路径 `gengxin_wei_win` / `gengxin_wei_linux`，**按当前运行环境选**：Windows 取 `_win`（`C:/...`），Linux/WSL 取 `_linux`（`/mnt/c/...` 或 `install --linux-prefix` 写出的前缀）；两行指向同一个文件夹。旧单行 `gengxin_wei: <路径>` 则按当前 OS 判断是否可访问，不可访问则询问用户。

### 本 skill 的 `xinxi.txt`（任务缺口板，MUST）

路径（固定）：`<本 skill 目录>/xinxi.txt`
即 `/home/xi/.pi/agent/skills/zhishiku-chuli/xinxi.txt`（Windows 同源 skill 目录下同名文件）。

**用途**：chuli **本轮/当前任务**是否有知识缺口、`caiji标记` 是 0 还是 1 的**磁盘真相**。压缩、岔话题、重载后仍以本文件为准；**禁止**只把标记留在聊天记忆里。

与续跑条分工：

| 文件 | 管什么 |
|---|---|
| `resume/current.md` | 链阶段 C0–C5 / 闭、下次动作 |
| **本 skill `xinxi.txt`** | **各任务表格**：有无缺口、`caiji标记`、标记明细 |

- 判定「有/无采集标记」→ **先读本文件当前任务节**的 `caiji标记`。
- 续跑条里的「采集标记：条数」是摘要，**与 `xinxi.txt` 双写**；冲突时以 `xinxi.txt` 各任务节为准，并回修续跑条。

#### 格式（一块任务一节，节间 `---`）

```text
# zhishiku-chuli 任务缺口板（磁盘真相；非会话记忆）
# 规则：一块任务一节；有缺口 → caiji标记：1 ；无缺口 → caiji标记：0
# 状态：进行中 | 已交付待采 | 已采清 | 闭

当前：有|无

---
任务：<可指认名或一句摘要>
领域：<名>
原路径：<绝对路径或未知>
状态：进行中
caiji标记：0
标记摘要：-
标记明细：
更新：<YYYY-MM-DD HH:MM>
---
```

有缺口时**同一任务节**改为（用户要的形态）：

```text
任务：heap-notes-uaf
caiji标记：1
```

完整节示例（`caiji标记：1` 时明细必填；**方案 A：层 + 反证 + 类型码**）：

```text
---
任务：heap-notes-uaf
领域：ctf-pwn
原路径：/path/to/chal
状态：进行中
caiji标记：1
标记摘要：层:错误 | E-新错误 | double free 后 tcache 未记
标记明细：
- 1 | 层：错误 | 缺什么：E-新错误 | 何时：卡片 3.2 free 后 | 反证：读过=cuowu.txt 相关段；对不上=无 double-free→tcache 条目；选错分叉=否；近似=- | 差在：cuowu 无此错与处理 | 当时判断：按常见 free 继续 | 如何越过：扫 ctf-pwn-workflow 后用 … | 用户原话：-
更新：2026-10-14 14:00
---
```

明细字段说明（`caiji标记：1` 每条 MUST；`如何越过` 可越过后补，其余**卡住当下写**）：

| 字段 | 取值 / 写法 |
|---|---|
| **层** | 只选其一：`路由` \| `卡片` \| `参数` \| `指令` \| `错误` \| `纠正` |
| **缺什么** | 类型码只选其一：`T-无树` \| `K-无卡` \| `P-参数/布局` \| `Z-无指令` \| `E-新错误` \| `U-用户纠正` \| `C-条件冲突` |
| **何时** | 卡在哪一步 / 哪张卡 / 哪个分叉 |
| **反证** | 固定四段：`读过=…`；`对不上=…`（条件逐条，禁「感觉不对」）；`选错分叉=是\|否`；`近似=卡号/节名或 -` |
| **差在** | 与「近似」的**一句**差异；无近似则写「无近似，缺整段」 |
| **当时判断** | agent 原打算怎么做 |
| **如何越过** | 越过后补：办法 / skill / 关键命令要点 |
| **用户原话** | 纠正类必填原话；否则 `-` |

**层 → 采写范围（给 caiji 用，chuli 摘要也可带层）**：

| 层 | 含义 | 采/回注侧重 |
|---|---|---|
| 路由 | 分诊/树进不去 | 新树 / 新探针 / 分诊 |
| 卡片 | 有技术、无步骤卡 | 新 `liucheng_biao` |
| 参数 | 卡有，尺寸/布局/条件细节无 | **只补**变体/条件，不整题重采 |
| 指令 | 缺可复制命令 | `zhiling` |
| 错误 | 新失败模式 | `cuowu` |
| 纠正 | 用户否定原判断 | 纠错路径 |

`标记摘要` 建议：`层:<层> | <类型码> | <一句差在>`，便于续跑条一眼看层。

#### 维护时机（MUST）

| 时机 | 动作 |
|---|---|
| 进入 chuli / 确定领域与题目后 | 若无该任务节 → **新建一节**：`状态：进行中`，`caiji标记：0`，`标记摘要：-`，`当前：有` |
| 步骤 5 反证通过且判定未记录 | **立刻**把该任务 `caiji标记` 写成 **`1`**；追加/合并 `标记明细`（含层/类型码/反证/差在）；改 `标记摘要`；写 `更新` |
| 同一类缺口再次出现 | **合并**同一条：同类 = 同 `层` + 同类型码 + 同 `近似`（或同何时锚点）；不无信息堆多条 |
| 不同缺口 | 明细多条；`caiji标记` 仍为 **1**（有任一缺口即 1） |
| 全程无缺口、任务完成 | 保持或确认 `caiji标记：0`；交付后该节 `状态：闭` 或删除；若无其它进行中节 → `当前：无` |
| 有缺口、用户侧已交付 | `状态：已交付待采`；**保留** `caiji标记：1` 与明细，供 caiji 读入 |
| 标记已用于开采或已声明无法采集 | 明细可注「已采/未采原因」；`caiji标记` 改 **0** 或节 `状态：已采清`/`闭`；无其它节 → `当前：无` |
| 用户取消任务 | 节 `状态：闭`，注明取消；半成品明细可留，不删已写样本指针 |

硬规则：

1. **有缺口 ⇒ 该任务表格 `caiji标记：1`**；无缺口 ⇒ **`0`**。不得口说有标却文件仍是 0。**仍只有 0/1**，不引入第三态。
2. 步骤 5 打标 = **写本文件**，不是只在回复里提一句；明细必须带 **层 + 类型码 + 反证 + 差在**（旧节缺字段 → 续跑/开采前补齐，或按无层降级整段采并注明）。
3. 步骤 6 分支前 **重读** 本文件当前任务节，按 `caiji标记` 决定采不采（分支仍只认 0/1）。
4. 本地模型模式：仍可写本文件打标（只读库、做题）；**禁止**据此直接写 caiji 库；交付后报告「有标记未采集（本地模型）」。
5. 本文件**不是**案例正文，不代替 caiji 的 `->` 块；只保留缺口位与摘要明细。
6. 无进行中任务时：文件头保留，正文 `当前：无`（可无任务节）。
7. **反证未过不得标 1**：未读就判缺、或「选错分叉=是」→ 先读/改路由，不打标（过程可记笔记，默认不采）。

## 领域

- 从用户请求判断领域，并**匹配 `gengxin_wei/` 下已有领域文件夹**（列 `gengxin_wei/suoyin.txt`）。
- 无匹配 → **询问用户**：属于哪个领域 / 是否新建领域库。
- 领域确定后不得中途更换。

## 处理协议

```text
- [ ] 1. 确定领域
- [ ] 2. 载入领域知识（总览 + 按需卡片，勿整目录塞进上下文）
- [ ] 3. 拆解用户请求为大步骤
- [ ] 4. 逐步处理（分诊 → 树选枝 / 并列择一 → 打开当前卡片 / 指令表 / 错误处理）
- [ ] 5. 遇候选未记录 → **先反证（读过/对不上/选错分叉/近似）** → 通过则写入 `xinxi.txt`（caiji标记：1 + 层/类型码/反证/差在/…），继续做完（此时不调用 caiji）
- [ ] 6. 任务完成后分支（**先读 `xinxi.txt` 该任务 `caiji标记`**）：
        · `caiji标记：0` → **直接把结果交给用户**（不 caiji / 不 tilian / 不 gengxin）；节改闭/`当前：无`
        · `caiji标记：1` → 先保证用户侧结果已交付（节：已交付待采），再 caiji → tilian → gengxin；采后清标记
- [ ] 7. 收尾记账（实战使用 + 生命周期；不挡交付）
- [ ] 8. IoT 领域 → 样本交接 ai_iot（见下「IoT 样本交接」）
- [ ] 9. 报告（有标记时写采集/回注情况；无标记时报告从简）
- [ ] 10. 交付物：在原题目目录留下 exp.py 与 wp（仅 pwn/CTF）
```

**1. 确定领域**：判断请求属于哪个领域，匹配已有领域库；无匹配就问用户。

**2. 载入知识（控制上下文）**：
- **必读**：`tieuli.txt` 要点、`liucheng/diaoyong.txt`（调用树「读法 + 探针 + 路由」）。
- **选技术**：用调用树探针观察题目 → 按路由规则命中技术/路径。岔路口**优先**看 `diaoyong` / 技术树；仅当 menkan 的 `<decision_points>` 带 `<source>`+`<confirm>` 时才可对照覆盖默认择一。
- **阶段门控**：若存在 `menkan/`，可读其 `<pipeline>` 作阶段 checklist；当前阶段信息未齐则补齐，**不改树、不替树选枝**。模糊 / 未确认的 menkan → 降级为参考。**`menkan/` 只读**，不得在本 skill 修改。
- **按需读**：命中技术的 `liucheng/shu/<标号>.md`（完整流程/入口退出点）；当前步骤的 `liucheng_biao/<标号>.txt`（一次一卡）；`zhiling.txt` / `cuowu.txt` 相关段；`yuanze`/`bianjie` 在需要裁决时读。
- **旧领域（无 `liucheng/`）**：回退到 `liucheng.txt` 的「入门分诊 + 树」。
- **禁止**：把整个 `liucheng_biao/` 或整份旧 `liucheng_jiu_shupai.txt` 无差别全文灌进上下文。
- 若存在 `tools/`，列出工具名，**按需**打开对应规范。

**3. 拆解请求**：把用户请求拆成有序的大步骤。

**4. 逐步处理**，每步按顺序查：

- **执行流（两层）**：
  1. 阶段门控（`menkan/workflow.xml` 的 `<pipeline>`）：先核对当前阶段信息是否已齐；未齐则补齐，**不改树、不替树选枝**。
  2. **选技术（调用树）**：用 `liucheng/diaoyong.txt` 的探针观察题目 → 按**路由规则**命中技术/路径（多探针可叠加）；技术清单查 `liucheng/jineng.txt`。旧领域回退到 `liucheng.txt` 入门分诊表。
  3. **走流程（技术树）**：打开 `liucheng/shu/<标号>.md` 看完整流程与**入口/退出点**，**可只走其中一段**（调用树可能只调部分路径）；再逐步对 `liucheng_biao/<标号>.txt` 卡片执行。
  4. **多节点同时满足（并列候选）**：分叉旁写着 `候选：A | B | C`（或卡片有 `## 并列`）且条件同时命中多个时，**不得随手挑**；跑
     ```
     python3 <skill 目录>/zhishiku-gengxin/scripts/yongfa.py <数据根>/<领域> --pick <键1,键2,...>
     ```
     按 **使用次数择一**（门槛：成次数 > 用次数 > 生命周期 > 命中 > 分诊表顺序），取胜出者。仅当 menkan `<decision_points>` **已确认**时可覆盖；无 menkan / 未确认 → 用此默认。胜出项「成」为 0（实战证据不足）→ 回退分诊表顺序取第一个，并在报告注明。
  5. 打开当前标号卡片 `liucheng_biao/<标号>.txt`，核对 **时机 / 条件**；不满足则走卡片「不满足时」或回到树分叉。
  6. 按卡片「做什么」执行，参数用实际值填充；完成后跟「下一跳」进下一卡。
  7. 总览写「尚未卡片化 / 见 jiu_shupai」时，**只翻** `liucheng_jiu_shupai.txt` 对应小节，不读全文件。
- `zhiling.txt`：取规范指令，填入参数后执行。
- `cuowu.txt`：预判可能出现的错误，按其「处理」提前规避或即时补救。
- `tieuli.txt` / `bianjie.txt`：遵守铁律，不越边界。
- `tools/<工具名>.txt`：任务需要某个专用工具时，读对应规范并照做。
  - **打靶机 / pwn 题需要「泄漏 libc 后确定版本」时 → 必读 `tools/libcsearch.txt`**，用 LibcSearcher 反查；多解必须 `add_condition` 消歧后再算 `system` / `str_bin_sh`；不得直接把泄漏地址当基址或跳过版本确认。
  - **领域为 `ai_iot` / IoT 固件相关时 → 必读 `tools/yangben-jiaojie.txt`**（样本交接规范），并在收尾时执行「8 IoT 样本交接」。

**5. 未记录情况（只打标 + 继续做完；此时不调用 caiji）**

判定为「未记录」的**入口情形**（仍要走下面反证；未过反证不得标 1）：

- 分诊选不进任何树，且 `liucheng_jiu_shupai` 也无对应节 → 候选层 `路由`、码 `T-无树`；
- 树上无匹配分叉 / 无对应标号卡片，且条件对不上 → 候选层 `卡片` 或 `参数`（有近似卡但条件/尺寸不够 → `参数` + `P-参数/布局` 或 `C-条件冲突`；完全无卡 → `卡片` + `K-无卡`）；

2. **处理中禁止调用 caiji**；**任务完成后：先读 `xinxi.txt`；`caiji标记：0` → 直接把结果交给用户（不采）；`caiji标记：1` → 先交付用户结果，再必须 caiji**（按已通思路复现再采）。有标记才是知识库增长入口；无标记禁止空跑采集链路。
3. **缺口处必须扫描所有可用 skill，优先求助能辅助的领域 skill**，而不是直接裸推；求助后**必须回到本 skill 的主流程**。
4. 进入 caiji 后**严格遵守 caiji 的规则**（如实、逐条、不攒写、失败也记；禁止回忆补写）。
5. **不直接改知识库**；回注只由 `zhishiku-gengxin` 做。**唯一例外**：收尾时经 `scripts/yongfa.py --tick` 写 `gengxin_wei/<领域>/yongfa.txt`（追加）与 `shengming.txt`（维护型状态表）。除这两个文件、且除经由该脚本之外，`gengxin_wei/` 下任何文件都不得写，也不得手改这两个文件。
6. **领域必须属于已有库**；不确定就问用户。
7. 不得因缺口而放弃任务，也不得**臆造**知识库里没有的知识。
8. **pwn/CTF 题完成后，必须在原题目目录留下 `exp.py` 与 `wp.md`**（已有同名文件先备份）；非 pwn/CTF 不触发。
9. **启用本地模型时：仅 chuli + ctf-pwn 可用；caiji / tilian / gengxin 一律禁用**（详见「本地模型边界」），防止污染 skill 与知识库。
10. **并列候选按使用次数择一**：同一分叉多个节点条件同时满足时，先按条件过滤，再经 `yongfa.py --pick` 裁决（成>用>生命周期>命中>分诊顺序），不得随手挑、不得只看书写顺序。
11. **`menkan/` 只读**：粗门控由 `zhishiku-gengxin` 维护（用户提供或 AI 提取经用户确认）；本 skill 不得改它。缺门槛 / 未确认 → 用默认择一门槛，报告「menkan 仅粗门控或待补」，不得臆造，也不得用模糊 point 压过调用树。

## 为什么会想略过标记 / 乱采（必须识破的借口）

| 借口 | 现实 |
|---|---|
| 这个缺口太小，不值得打标 | 小缺口正是知识增长点；标 **层:参数** 即可，caiji 只补变体，不整题重采；不写 `xinxi` → 永远是缺口 |
| 条件差一点就当整条技术缺口 | 先反证；有近似卡 → **层:参数** + 差在；不要抬成路由/无树 |
| 没读卡就标「库里没有」 | **反证：读过** 未写清 → 先读，不标 |
| 选错分叉也打标去采 | **选错分叉=是** → 改路由，默认不标 |
| 做的时候已经懂了，完成后不必 caiji | **`caiji标记：1`** 就必须采；否则下次还是未记录。**`0`** 则本来就不必采，直接交结果 |
| 最终做通了，说明库其实够用，不用标 | **能做完 ≠ 无缺口**；卡过且反证对不上 → 交付前 6.0 自检必须改成 1 |
| 无标记也要先写完报告/tick/库务再给用户看 | **禁止**；`caiji标记：0` → **先/直接**交结果，tick 不挡交付 |
| 处理中顺便开 caiji 边做边采 | **禁止**；打断主任务；**做完并交付后再采**（仅当 `caiji标记：1`） |
| 完成后用总结写进 caiji，不再复现 | 总结 = 污染；必须按已通思路**复现**再写 `->` |
| 知识库没有，我随便试一下又不标 | 试可以，但必须写 `xinxi.txt` 该任务 `caiji标记：1`，否则白试 |
| 缺口我用通用能力解决了，就不用采了吧 | 解决了更要写板、完成后更要采——下次才变「已记录」 |
| 缺口我自己会，不用去找别的 skill | 找 skill 是为了复用已验证方法；`xinxi` 明细写清用了谁 |
| 我直接硬解更快 | 硬解易错且不沉淀；先扫 skill，再动手，并写 `xinxi` |
| 标记只在回复里提一句，不写 `xinxi.txt` | 压缩/重载后标记蒸发 → 当成「会话内维护即可」的旧借口；**必须落盘** |
| `xinxi` 仍是 0，却口头说有缺口去空跑/漏跑 caiji | 分支只认文件里的 `caiji标记` |

## 红旗（出现任意一条，立即停下修正）

- 我遇到了知识库没有的步骤，却**不写 `xinxi.txt`（该任务仍 `caiji标记：0` 或根本无节）**。
- 我**跳过步骤 6.0 交付前自检**，把曾卡住/新错误/用户纠正的题直接闭成 `caiji标记：0`。
- 我打了标，明细却**无层 / 无类型码 / 无反证 / 无差在**（方案 A MUST；旧节开采前应补齐）。

- **`caiji标记：0`，却不把结果交给用户**（还在空转库务/caiji/长报告）。
- **`caiji标记：1` 时先采完库再让用户看到结果**（应先交付，再采）。
- 完成后开 caiji 却用**总结/回忆**填 `结果`，不复现；或不读 `xinxi` 明细靠脑补标记。
- 我改了知识库里的文件（应该由 gengxin 做）。
- 我在缺口处反复试错，却既不写 `xinxi` 也不在明细里留下越过方式。
- **我遇到缺口，没扫描其他 skill 就直接硬解**。
- **多个候选条件同时满足，我随手挑了一个（没跑 `--pick` / 没看使用次数）。**
- **我改了 `menkan/`，而不是只读它。**

- 无任何未记录，我却「习惯性」开 caiji。

- **本地模型模式下用本地模型「总结」冒充采集结果，或直接改 gengxin_wei**。

## 启动自检

处理前：

- 领域库存在，且 `liucheng.txt` / `cuowu.txt` / `zhiling.txt` 至少有一个非空。
- 若 `liucheng.txt` 为树形总览：确认读法/分诊可读；需要执行时能打开对应 `liucheng_biao/<标号>.txt`。
- 引用的知识条目能对上（`来源` 可读）。

处理前（另）：

- 已 read 本 skill `xinxi.txt`；若有未闭且 `caiji标记：1` 的旧任务节，先按续跑/用户意图决定续采还是新开节，**禁止**静默丢旧标记。

处理中遇缺口时：

- 已写入本 skill `xinxi.txt`：该任务节存在且 **`caiji标记：1`**，明细含层/类型码/何时/反证/差在/当时判断（越过后补如何越过）；不得只放在嘴上。
- 已扫描其他 skill；选中的 skill 已读并遵循；越过缺口后已回到主流程。
- **未**在处理中途打开 caiji。

任务完成后：

- **用户侧结果已交付**（答案/产物/结论可见；适用时 exp/wp 已落盘）。
- 已 **read `xinxi.txt`** 再分支。
- `caiji标记：0` → 确认未调用 caiji/tilian/gengxin；未用库务挡住交付；节已闭/`当前：无`。
- `caiji标记：1` → 交付之后 `zhishiku-caiji` 已按 **`xinxi` 明细**复现采集；不可用 → 在已交付前提下报告「有标记未采集」，**保留**文件中的 1 与明细。
- 若已采集，确认缺口已进入 `gengxin_wei/<领域>/`（tilian→gengxin 完成）或已说明待回注；并已把该任务 `caiji标记` 清 0 或节闭。
- 收尾已跑过 `yongfa.py --tick`（含空轮次，且**不挡交付**）；或已明确注明「未记账（本地模型模式）」。
- 若输出提到「生命周期归零」：已汇总询问用户，并按答复执行了 `--expire` / `--refresh`（无答复则停在 `待裁决`）。

3. 命中 liucheng 分诊/树 → 打开当前标号卡片，按「做什么」逐条执行

   - cuowu.txt 预判「解释器不可用」：python3 可能失败 → 备选 python
4. 全程有知识；`xinxi.txt` 该任务保持 `caiji标记：0`

6. 不 caiji；节闭 / `当前：无`；交付后 `--tick`；报告从简：领域 python-env / 标记 0

  → 不调用 caiji；扫描 skill，按「权限 / 提权 / sudo」匹配并遵循

## 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 遇到缺口不写 `xinxi.txt` | 完成后无 caiji，知识库永不增长 | 反证通过 → 该任务 `caiji标记：1` + 层/类型码/反证/差在明细 |
| 明细无层/无反证 | caiji 只能整段采、易误标 | 方案 A 字段写全；参数层与路由层分开 |
| 只在聊天打标、不落 `xinxi` | 压缩后标记丢失 | 打标=写本 skill `xinxi.txt` |
| 处理中途就开 caiji | 打断主任务、边界混乱 | 做完再按 `xinxi` 采 |
| `caiji标记：1` 完成后不采 | 缺口永远在 | 有 1 → 必须 caiji |
| `caiji标记：0` 却开 caiji | 空案例 / 重复采已有知识 | 0 不采，直接交用户结果 |
| 标记 0 仍先写长库务再给用户 | 用户等结果，体验差 | 0 → 直接提交结果 |
| 标记 1 先采库再交结果 | 用户被采集卡住 | 先交付，再 caiji |
| 完成后总结填库、不复现 | 采样污染 | 按已通思路复现，照抄 stdout；标记来自 `xinxi` 明细 |
| 直接改知识库 | 绕过 gengxin 的安全规则 | 回注交给 gengxin |
| 领域猜错 | 用错库、知识进错地方 | 不确定就问用户 |
| 采集时攒着写 | 数据失真 | 遵守 caiji 的采集节奏 |
| 缺口处放弃任务 | 任务失败 | 打标 + 扫 skill / 通用能力继续做完 |
| 缺口不扫 skill、直接硬解 | 重复造轮子、标记质量差 | 先扫所有 skill，优先求助匹配的 |
| 求助其他 skill 后不返回主流程 | 脱离知识库系统 | 越过缺口后必须回到 chuli |
| 臆造知识库没有的知识 | 知识失真 | 只用库里有的；缺口靠标记+完成后采集补 |
| 用户纠正了判断却不打标不采 | 最值钱的纠错样本丢失 | 知识性纠正打标；完成后 caiji 记 `用户纠正` 块 |
| 用知识却不跑 `--tick` | 实战统计与生命周期都不动 | 收尾必须记账 |
| 空轮次跳过记账 | 生命周期不倒计时 | 没用到知识也要跑 `--tick` |
| 手改 `yongfa.txt` / `shengming.txt` | 哨兵或状态被改坏 | 只经由 `yongfa.py` |
| 生命周期归零却自作主张 | 越权替用户决定 | 汇总成一次问；没答复停在 `待裁决` |
| 本地模型参与 caiji/tilian/gengxin | 案例与容器被胡写污染 | 本地模型仅 chuli+ctf-pwn；写库须关本地模型后由主 agent 走原链路 |

| 改了 `menkan/` | 门控失真 | `menkan/` 只读；由 gengxin 按用户确认写 |
