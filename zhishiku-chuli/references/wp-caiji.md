## WP 与采集的关系（MUST）

**wp 只是加速选枝，不是免采集票。** 恰相反：依据 wp 复现成功、而库内没有对应卡时，这份「wp → 本机复现」本身就是最值得沉淀的缺口。

| 情形 | 是否仍要查缺口 / 打标 |
|---|---|
| wp 找到且**依据它复现通**，库内无对应卡/流程 | **MUST** 走步骤 5 反证；反证过则 `caiji标记：1` |
| wp 找到，但库内**已有**完整对应卡，只是拿 wp 加速 | 仍查缺口；查到确有缺再 `1`，无线索得 `0`（不得因「库盖过」直接放弃排查） |
| wp 找到但**本机不符**（改保护/改 libc/去符号），靠库修正做通 | **MUST** 打标（层=参数/布局），这正是库该补的 |
| wp 找到但**没能复现**、改用库内路做通 | **MUST** 查缺口；库内路是否新、是否踩坑都要记 |
| wp 全失败/无网 | 照常步骤 5；不得拿「wp 没有」当不采集的理由 |

收尾强制动作（绑定步骤 7）：

1. 交付用户前，**再读一次 `xinxi.txt` 当前任务节**——不要靠开场读到的旧印象。
2. 本轮**用过 wp**（不论成/败）→ 必须显式回答一句：「本轮有 wp，缺口已查：有/无」。
3. 查到有缺口 → `caiji标记：1` + 明细，**先交付再 caiji**；不得因 wp 跳过。
4. 查到无缺口 → `caiji标记：0`，并说明「库内已有覆盖：<卡号>」；这类才允许 `0`。
