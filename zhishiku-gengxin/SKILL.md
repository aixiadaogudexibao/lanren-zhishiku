# 知识库回注 / 领域分化容器（zhishiku-gengxin）

## 概述

把知识库（`tilian_wei`）里的知识，**按领域**回注到知识容器 `gengxin_wei/` 下对应领域的文件夹。

**一个领域 = 一个文件夹**，知识不跨领域混放。本 skill 只维护 `gengxin_wei/` 里的文件，不动别处。

> 定位：本 skill 是**知识容器 / 素材库**，不是解题器。它把知识按领域沉淀好，供人或 AI 起草领域 skill 时取用。

## 流水线定位

```text
zhishiku-caiji（采集） ─▶ 案例 ─▶ zhishiku-tilian（提炼） ─▶ 知识库
                                                              │ 提炼完成后链式
                                                              ▼
                                          zhishiku-gengxin（按领域回注到容器）
```

| 需求 | 用哪个 |
|---|---|
| 小任务队列 / 每日任务 / 执行次数 | `planing-biao` |
| 长跑项目 / 需求 / issue / 迭代 | `chang-plan` |
| 执行留痕、采集案例 | `zhishiku-caiji` |
| 把案例提炼成知识点 / 执行流 / 错误处理 | `zhishiku-tilian` |
| 用知识库处理某领域任务 | `zhishiku-chuli` |
| **把知识按领域回注到容器** | **本 skill** |

上游：读 `zhishiku-tilian` 的知识库（`tilian_wei`）；上游不可用 → 不写入，报告「未回注」。

## 领域怎么定（关键：问用户）

- 一个领域 = 一个文件夹，名字由用户定义（如 `ctf-pwn`、`web`、`python-env`）。
- 领域来源优先级：
  1. **上游 `zhishiku-tilian` 传入的领域**（首选）→ 直接用；
  2. 调用时参数已指定 → 直接用；
  3. 否则 → **必须询问用户**，不得臆断、不得沿用上次结果。
- 询问时**先列出 `gengxin_wei/` 下已有领域**，让用户选或新建；避免同一领域被写成多个名字（如 `python` 与 `python-env`）。
- 非交互执行且未指定领域 → **不写入，只报告**「待回注的知识 + 建议领域」，等用户下次确认。
- 首次遇到的新领域 → 创建骨架文件夹。

## 跨平台路径解析（MUST）

`xinxi.txt` 为每个数据根保留**两行**，指向**同一个文件夹**（Windows 与 Linux 双端共享同一份知识容器）：

```text
gengxin_wei_win: <Windows 数据根绝对路径>
gengxin_wei_linux: <Linux 数据根绝对路径>
```

按当前运行环境选取：

- **Windows** → 取 `gengxin_wei_win`（形如 `C:/Users/<用户>/...`）。
- **Linux**（含 WSL）→ 取 `gengxin_wei_linux`（形如 `/mnt/c/Users/<用户>/...`；
  挂载前缀不是 `/mnt/c` 的机器，以 `install --linux-prefix` 写出的那一行为准）。
- 旧单行 `<根名>: <路径>` → 按当前 OS 判断是否可访问；不可访问 → 询问用户补写另一平台路径，改回两行格式。

两行必须指向同一份数据根；不一致 → 停下询问，不得自行挑选。

## 领域文件夹骨架（新建领域时生成）

每个 `.txt` 首次创建时写入一行表头 + 尾部哨兵（仅 append-only 的两个文件需要哨兵）：

```text
tieuli.txt     -> # 铁律
yuanze.txt     -> # 概述原则
bianjie.txt    -> # 边界
cuowu.txt      -> # 常见错误
liucheng/           -> # 两层执行流：diaoyong.txt（调用树，含读法+探针+路由）\n  jineng.txt（技术树清单）\n  shu/（技术树本体，一技术一 .md）（模板见 templates/liucheng/）
liucheng.txt        -> # 全标号索引（validate 依赖；保留卡片标号），+ 旧树形总览
menkan/             -> # 门槛目录，放 workflow.xml（阶段门控/判定点/清单；模板见 templates/menkan/workflow.xml）
liucheng_biao/      -> # 空目录；回注时按标号落卡片
zhiling.txt         -> # 命令速查
suoyin.txt          -> # 案例id | 产出条目\n★
yongfa.txt          -> # 实战使用日志（写入位＝文末哨兵行）\n★
shengming.txt       -> # 生命周期表（维护型；首次 --tick 时生成，不必预建）
rizhi.txt           -> # 更新日志\n★
_snap/              -> # 空目录；回注前由 snapshot.py --take 生成
tools/              -> # 该领域专用工具的使用规范（一个工具 = 一个 <工具名>.txt）
```

### `tools/`（领域专用工具）

`<数据根>/<领域>/tools/` 存放**本项目/本领域专用工具的使用规范**，与知识条目分开管理。

- **一个工具 = 一个 `<工具名>.txt`**（如 `libcsearch.txt`）；文件名小写、无空格。
- 每个工具文件至少包含：**何时用（触发条件）/ 安装位置 / 使用规范 / 常见错误 / 边界**。
- **触发时机**：当某个工具在案例里被反复使用、且使用者容易忘记怎么用时，就为其建规范。
- **与 `zhiling.txt` 的区别**：`zhiling.txt` 是「单条命令速查」；`tools/<工具>.txt` 是「工具级的完整使用规范（含环境、消歧、坑）」。简单到一行命令就能表达的不建 tools 文件。
- **回注来源**：由 `zhishiku-tilian` 提炼结果或用户直接指定回注；新建/更新后在 `rizhi.txt` 记一笔。
- **不属于采集指标**：`tools/` 是工具手册，不计入 `suoyin.txt` 的「案例id | 产出条目」统计。

## 写入准入（MUST · 防垃圾场）

知识容器是**可复用指令/原则库**，不是某次实验的垃圾桶。回注前对每条候选过门；不过门 → **不写入**，只在报告里列出「已拒绝 + 原因」。

### 文件类型隔离（MUST · 堵乱放）

**一类文件只装一类东西**；写错类型 = 污染，必须改归属或拒绝，不得「先扔进最近的文件」。

| 文件 | **只准** | **禁止** |
|---|---|---|
| `tieuli` / `yuanze` / `bianjie` | 跨案例原则、边界 | 具体命令表、某 CASE 资产清单、PoC 剧本 |
| `cuowu` | 可复用故障：现象→原因→处理 | 某次实验完整流水；与错误无关的指令教程 |
| `liucheng.txt` + `liucheng_biao/*` | **路由 + 必要判断 + 本步抽象动作** | 案例资产总表；工具手册全文；zhiling 速查表；某次实验绝对路径/脚本名/端口实参当正文 |
| `menkan/`（如 `workflow.xml`） | **大概流程**：阶段门控 / 判定点 / 检查清单 | 具体步骤与命令（属卡片）；某次实验资产；无来源/未确认的 AI 提取项 |
| `zhiling.txt` | 跨案例**工具/环境**单行命令（通名占位） | PoC/注入调用行；案例号当参数；过泛 `cat`/`ls` |
| `tools/*` | 某一工具的完整用法 | 执行流步骤路由；多案例 exp 文件名清单 |
| `yongfa` / `rizhi` / `suoyin` | 日志与索引 | 当知识正文用 |
| `_snap/` | 回滚副本 | 不当活知识读、不往里面「修正」冒充现行 |

**执行流更严（硬）**：

1. 卡片只留：**时机 / 条件 / 不满足时 / 做什么（抽象）/ 参数 / 下一跳 / 来源**；可选极短 `## 实例`。新回注优先用扩展头：**目的 / 最小前提 Min / 手段 Means（可选）/ 实例·绑定 Bind**（见下「目的分层」）；旧卡未改前仍认「条件」。
2. `## 做什么` / `## 条件`（或 Min）只写**必要判断**（例：能收包→完整协议；`gets` 类→按栈溢出枝走；相对路径须先进 rootfs）。
3. **禁止**在卡片里放：多案例「环境根资产索引」表、某固件函数地址长链、某 PoC 文件名、lab 绝对路径、完整 tools/zhiling 拷贝。
4. `## 实例` 若有：必须通名（`rootfs目录`/`服务程序`/`端口`）；**禁止**写死 `tddp`/`1040`/`unpack/sr20/...`/`CASE-xxxx`。案例名只出现在 `## 来源`。
5. 口诀：换无关案例，这张卡的正文是否仍成立？否 → 删或下沉到复现笔记 / yangben 登记，不留在 liucheng。

### 目的分层与条件过拟合（MUST · ctf-pwn 试点已开，其它领域同纪律）

设计对照：知识库根 `设计-技术框架草稿.md`；试点目录 `gengxin_wei/ctf-pwn/{mudi,jishu,silu,buju,huanjing}/`；旧 `diaoyong.txt` 仍可接题，**新回注不得再加长「样题全貌 ∧」**。

**两根轴**：
- 文档层：目的说明 / **技术（单机制）** / **思路（选型串链）** / 环境·布局标签
- 能力目的：`R` 侦察 · `L` 泄漏 · `W` 写 · `A` 分配 · `C` 控流 · `X` 约束执行 · `S` 特殊通道（不是 H/S/K 载体）

**回注执行流时**：

| 写什么 | 规则 |
|---|---|
| **一条技术一个主目的** | ID/树前缀只服务 L 或 W 或 A 或 C…；禁止再新建「泄+写+hook+orw」捆成一棵的剧本树 |
| **Min（最小前提）** | 只留机制成立所需的**可观察原语/布局标签**；少而硬 |
| **Means** | 同一机制的可选实现 **A/B 并列**，不是「必须全满足」的样题清单 |
| **Bind** | 题名、菜单串、具体长度、QEMU 开关、接口专名 → 只进来源/实例 |
| **思路** | 「无 show 怎么选 L」「按 glibc 选 C」→ 独立 `silu/` 或路由薄规则，**不要**写进技术 Min |
| **环境 Env / 布局 Layout** | 保护、glibc 档、seccomp、有无 show → 思路过滤；堆形态标签 → 匹配 Min；**二者都不是整树唯一触发器** |
| **辅助 means** | consolidate、切块等 **不是目的大类**；挂 `means.*` 或作技术 Means |

**过拟合拒绝（不过门则不写入 Min / 不写入 diaoyong 硬门槛）**：

1. Min 或路由 ∧ 中出现**单题接口名**、单题菜单文案、单次 lab 路径/开关组合 → 降为 Bind。
2. **换题测试**：去掉来源题环境后，条件是否仍陈述同一机制？否 → 重写或拒绝。
3. **命中=1** 的新树：路由只准挂 Min 级标签；须在 jineng/别名标「单样本，手段可替换」。
4. **禁止**用「该题成功路径上出现过的一切」生成 `diaoyong` 长 ∧；∧ 只连接 Min 级能力/布局。
5. 旧树（如 H.policy / H.rexp）**拆链回注**：按 L/W/A/C/X 分条 + silu 串链；并行试点文件优先写 `jishu/`·`silu/`·`diaoyong_mudi.txt`，不强制删旧卡。
6. 口诀补强：换无关题，**触发条件**是否仍成立？否 → 条件过拟合，与「路径/PoC 名」同等拒绝。

**卡片字段（新回注优先）**：

```text
## 目的
## 最小前提          ← 匹配/路由只看这
## 手段（可选）      ← A/B 并列
## 不满足时          ← 相对 Min
## 做什么
## 实例/绑定         ← 样本 only
## 下一跳            ← 目的级或技术 ID
## 来源
```

**自检加项**：
- [ ] 新树/新卡是否只有一个主目的？
- [ ] Min 是否含题专名/样题整貌？
- [ ] 多目的链是否拆成技术 + 思路，而非一棵巨树？

### 准写（目标内容）

- 领域内可复用的：铁律 / 原则 / 边界 / 常见错误 / 执行流卡片 / **通用**命令速查 / 工具规范
- 用户**明确点名**要回注的范围（例如「只回注 debvm 与传文件」）→ 严格按范围，不顺手塞别的
- 对已有条目的**必要补丁**（旧命令缺关键坑，如「相对路径须先 cd rootfs」）

### 禁止写入（非目标 / 污染）

| 类型 | 例 | 应去哪 |
|---|---|---|
| 一次实验的绝对路径/文件名 | `/root/CASE-0002/...`、`arm64-debug.ext4`、`sr20_tddp_rce.py` | 案例笔记 / 复现 md，**不进** zhiling / 卡片正文 |
| 案例号当命令参数或卡片实例 | 指令/实例里写 `CASE-0002`、某固件代号 | 只允许出现在「来源」列 |
| **某次实验的 PoC/注入剧本** | `python3 脚本 ...`、客机本机打/主机外打整段、poc-*.md | **复现/案例**；不进 zhiling、常用指令、执行流正文 |
| **案例资产总表进执行流** | A.repro 里 CASE→rootfs/exp 对照表 | `tools/yangben-jiaojie` / 环境根 registry |
| 过宽的万能命令 | 单独一条 `cat 文件`、`ls` | 不建条 |
| 与已有行同义重复 | qemu 绝对路径平行条 | 合并 |
| 桌面草稿/会话摘要 | 未提炼聊天 | 不回注 |
| 用户未要的「顺手优化」 | 改范围外文件 | 禁止 |
| 无来源 | 「我觉得」 | 禁止 |

**口诀（zhiling / 常用指令 / 卡片实例）**：换一个无关案例，这条是否仍原样有用？否 → 不写入该类文件。

### `zhiling.txt` 指令列写法（强制）

```text
操作 | 位置 | 指令（规范形式） | 命中 | 来源
解 gzip 的 tar 包 | 终端 | tar -xzf 压缩包 | 1 | <领域>/<案例> …
```

1. **指令列**只用**中文通名**占位：`样本` `固件` `目录` `压缩包` `端口` `磁盘镜像` `rootfs目录` `服务程序` `脚本` `目标IP` …
2. **禁止**在指令列写：案例号、CVE、厂商设备名、某次实验绝对路径、某次 PoC 文件名、lab 专用主机名。
3. **来源列**才写案例/步骤溯源（`ai_iot/CASE-xxxx …`）；来源 ≠ 参数。
4. 同操作已存在 → **改旧行**或放弃，不新增近义行。
5. `tools/` 已写全的流程，zhiling 只留**一行入口**；细节不在 zhiling 再堆一份。
6. zhiling **只收工具/环境向**命令（debvm、传文件、解压、qemu-user…）；**不收**案例 PoC 调用行。
7. **不删旧条目**除非用户明确要求删除；清理重复时先报告再动。

### 回注前自检（清单）

- [ ] 是否在用户/上游指定的领域与范围内？
- [ ] 指令列是否零案例名、零实验绝对路径？
- [ ] 归属文件类型是否正确（卡片≠登记表≠zhiling≠tools）？
- [ ] 是否与现有 zhiling/tools 重复？
- [ ] 是否太泛（任何领域都适用的 shell 常识）？
- [ ] 是否有来源？
- [ ] 是否误删或改写范围外旧条？
- [ ] **执行流**：主目的是否唯一？Min 是否过拟合样题？多目的是否误捆一树？

任一项不通过 → 该条不写入。

## 条目格式（固定，便于幂等合并）

```text
- <要点一句话>
  来源：<领域>/<案例id> buzou/<NN>.txt 步骤<字母>
  命中：<N>
```

命令速查为表格行，必须带 `来源`。执行流按下方「树形格式」写，卡片与总览都要能溯源。

### 执行流结构（两层 · 正式 · 人与 agent 共用）

执行流**不再**以「整文件竖排 1.2.3.」为权威形态，而是**调用树 / 技术树 两层分离**：

```text
liucheng/                # 两层结构
├─ diaoyong.txt          # ① 调用树：接题探针 + 路由（只选技术/选路径，无步骤细节）
├─ jineng.txt            # ② 技术树清单：登记所有技术（用途/入口/复用/常被谁调）
└─ shu/<标号>.md         # ③ 技术树本体：一技术一文件（完整流程，可部分调用）

liucheng.txt             # 全标号索引（保留；validate 依赖）+ 旧树形总览（兼容旧引用）
liucheng_biao/<标号>.txt # 一步一卡的细化步骤（被技术树引用）
```

**为什么要两层**：不同分支可能用**同一技术**（技术树共享一份，不重复写）；同一技术可能有**不同用法或只被调用部分路径**（技术树内部分路径/入口）。所以：
- **调用树只管「根据题目思路选技术/选路径」**；
- **技术树写该技术的完整流程**；
- **调用树可只调用技术树的一段**（技术树标注入口/退出点）。

#### 1a）调用树 `liucheng/diaoyong.txt` 结构（MUST）

```text
# 调用树 · 接题 → 探针 → 调技术树
## 怎么用        接题 → T.0 → 用探针观察 → 按路由规则匹配 → 调 shu/<技术>.md（从入口走，可只走一段）
## 探针集        可观察量清单（P1 保护 / P2 结构 / P3 漏洞形态 / P4 输出 / P5 沙箱 /
                 P6 地址 / P7 输入语义 / P8 目标环境）——可随领域扩展
## 路由规则      [P?:值] ∧ … → 标号（调哪些段）；※ 注明“只调部分路径”
## 技术复用      同一技术被多处调用时，都指向 shu/ 同一份
## 只调用部分路径  列出“只走某一段”的常见情形
## 兜底          探针全不命中 → 判为缺口 → 触发 caiji
```

- **探针 = 可观察量**（保护位 / 结构 / 漏洞形态 / 输出行为 / 沙箱 / 地址 / 输入语义 / 环境）。**多个探针叠加**使用，不是互斥 if-else。
- **路由规则用逻辑组合**写法（`[P2:…]∧[P3:…] → 标号`），写清“**什么条件调哪棵技术树的哪段**”。
- **必须写兜底**：探针全不命中时 → 判缺口（不得让分叉无路可走）。
- **只选技术，不写步骤/命令/偏移**（细节下沉 `shu/` 与卡片）。

#### 1b）技术树清单 `liucheng/jineng.txt` 结构（MUST）

登记所有技术树，字段：标号 / 名称 / **用途** / **入口** / 可分叉 / **常被谁调**；末尾可画复用关系。

```text
## 技术清单
| 标号 | 名称 | 用途 | 入口 | 常被谁调 |
| T.0  | …    | …   | T.0  | 所有      |
## 复用关系
（画：某技术 ← 谁调它）
```

- **入口**：可从哪个步骤进（供部分的调用）；**常被谁调**：哪些路由/技术引用它。
- 新增一棵技术树时，**必须同时登记到本文件**。

#### 1c）技术树本体 `liucheng/shu/<标号>.md` 固定字段（MUST）

> **写法硬要求**：「完整流程」每一步用**一句描述到位的话**。
> - **必须展开缩写**（如 `mh`=`__malloc_hook`、`δ`=偏移、`ogg`=one_gadget、`P`=PREV_INUSE 位、`FD/BK`=空闲块 fd/bk），不得只写 `fd → mh-δ` 这种电报简写。
> - 每步要点明「**这步在干什么 + 关键值/公式**」，**不看卡片也能读懂**。
> - 但不搬卡片全文（卡片仍是“能照着敲”的极细步骤）；技术树写“能读懂”，卡片写“能照做”。
>
> 对照示例：
> - ✗ 坏：`H.hook.2 fd → mh-δ`
> - ✓ 好：`H.hook.2 改 fd：把假块的 fd 指向 __malloc_hook-0x23（该处字节恰为 0x7f，可当 0x70 fastbin 的合法 size）`

```text
# 技术树 · <标号>（<技术名>）
> 类型：堆/栈/… ；缩略语：… ；细化步骤：liucheng_biao/<标号>.N.txt；调用方式：见 diaoyong.txt

## 用途
## 前置条件（进入本树的门槛）
## 完整流程（每步一句、描述到位、含内部分叉）
## 入口 / 退出点      ← 供调用树「部分调用」
## 内部可分叉
## 被谁引用           ← 哪些路由/其它技术调它
## 复用               ← 它自己调用哪些其它技术
## 来源
```

#### 1d）`liucheng.txt` 全标号索引（保留）

#### 3.1）并列候选（一棵树的同一分叉有多个解）

## 回注算法

```text
0. **先拍快照**：snapshot.py <数据根>/<领域> --take --note "回注 <案例id>"（失败则停）
1. 确定本次的领域（参数 / **询问用户**；非交互且未指定则只报告不写入）
2. 定位领域文件夹；不存在则创建骨架
3. 读知识库五类产出（或用户点名的文件），按映射分组
4. **准入过滤**（见「写入准入」+「文件类型隔离」）：非目标/污染/无来源/纯重复/写错文件类型（如资产表进卡片、PoC 进 zhiling）→ 拒绝或改归属，不进入错误文件
5. 逐条 diff 合并到知识文件（tieuli/yuanze/bianjie/cuowu/zhiling + 执行流树/卡片 + 范围内 tools + 已确认的 menkan 门槛）：
   - KB 有、文件无        -> 追加（执行流则写/改 liucheng.txt 树节点 + liucheng_biao 卡片）
   - 两边都有（同要点/同标号） -> 取更完整 / 命中更高的一条替换；zhiling 同操作合并不平行堆
   - 文件有、KB 无        -> 不删，标 [候选过期] 并在报告列出
   - 范围外文件           -> 不动
6. 追加领域 suoyin.txt 一行（案例 -> 产出了哪些条目；被拒条数可写在备注）
7. 更新全局 suoyin.txt（该领域的最后更新时间与条目数）
8. 追加 rizhi.txt 一行（append-only），**行尾带快照名**：
   `<日期> | 回注 <领域>/<案例id>：<变更摘要>；拒绝 N | 快照 <YYYYMMDD-HHMMSS>`
9. 报告：领域 / 新增 / 更新 / 拒绝（原因）/ 候选过期
```

`yongfa.txt` **不在回注范围内**：它由 `zhishiku-chuli` 写入，本 skill 只读、不合并、不改写。

## 实战使用日志 → `yongfa.txt`（append-only，末尾 ★）

记录**知识条目在实战中被用了几次、结果如何**。写入方是 `zhishiku-chuli`（收尾时追加）；`gengxin` 只读，用于剪枝判断。

### 与条目里 `命中` 字段的分工（MUST 分清）

| 字段 | 含义 | 谁写 | 何时 +1 |
|---|---|---|---|
| 条目里的 `命中：N` | **来源支撑数**：多少个案例样本印证了这条知识 | `tilian` 重复提炼 | 同要点再次被提炼出来 |
| `yongfa.txt` | **实战效果**：真的用了几次、成/败各几次 | `chuli` 收尾 | 每次任务用到该条目 |

两者不能合并：来源支撑数高 ≠ 实战好用；而「实战老失败、却只有一条来源」的知识，正是要抓出来的。

### 格式

```text
# 实战使用日志（append-only；写入位＝文末的哨兵行）
# 日期 | 键 | 结果 | 案例id | 备注
2026-09-27 | liucheng_biao/<标号> | 成 | <领域>/<案例号> | -
2026-09-27 | tools/<工具名> | 败 | <领域>/<案例号> | 多解未消歧
★
```

- 键 = `<文件>/<标识>`，标识取该文件里的稳定名字：

| 类型 | 键 | 例 |
|---|---|---|
| 执行流卡片 | `liucheng_biao/<标号>` | `liucheng_biao/H.leak.3` |
| 工具规范 | `tools/<工具名>` | `tools/libcsearch` |
| 错误处理段 | `cuowu/<错误特征>` | `cuowu/权限被拒` |
| 命令速查行 | `zhiling/<操作>` | `zhiling/搜索本地软件` |

- 结果 ∈ `成` / `败`（只有两态；早期设计里的「部分」已废除——判不准就记 `败`，别留中间态）。
- 案例id 写 `<领域>/<编号>`；当次没有对应案例（未触发采集）写 `-`。
- 备注一句话说明败因；无则 `-`。**任何字段都不得含 `|`**。
- **铁律 / 概述原则 / 边界不计数**（条目短、总量小，被违反时由用户直接指出即可）。
- 追加 = 一次替换，不读全文：

  ```text
  Edit: oldText = "★"
        newText = "<新行>\n★"
  ```

- **只追加，不改历史行**：历史行是「当时实际发生了什么」的事实记录，改了就没意义。
- **表头/注释行里不得出现 `★`**（否则写入位歧义，也破坏「全文件唯一」）。

### 派生统计（剪枝的依据）

用 `scripts/yongfa.py` 算，不要手数：

```bash
python3 <skill 目录>/scripts/yongfa.py <数据根>/<领域>
```

输出三张表：**用过** / **生命周期** / **零使用**（零使用默认列 40 项，`--all` 看全量）。

并列候选择一（决策树多个节点同时满足时，`chuli` 用它裁决，别手数）：

```bash
python3 <skill 目录>/scripts/yongfa.py <数据根>/<领域> \
  --pick liucheng_biao/H.cat.1,liucheng_biao/H.cat.2,liucheng_biao/H.cat.3
```

- 门槛：**成次数 > 用次数 > 生命周期 > 命中 > 输入（分诊表）顺序**。
- 输入顺序即分诊表/树的书写顺序，用作最后兜底（等价「默认取第一个」）。
- 胜出项「成」为 0 → 实战证据不足，等价回退分诊表顺序；报告里要注明。

判读：

- `成=0 且 败>=2` → 失败证据充分，可直接列进「候选过期」，不必等观察期。
- `用0` → 长期没人用：可能是真没用，也可能是总览没挂上它。**先查树，别直接删**。
- 生命周期归零 → 见下一节「条目生命周期」，**必须询问用户**。
- 统计只作**依据**；动作仍按上面铁律「不删条目」——只标 `[候选过期]` 并报告，删除交给用户。

## 条目生命周期 → `shengming.txt`（维护型，非 append-only）

`yongfa.txt` 回答「用了几次」；`shengming.txt` 回答「**多久没人用了**」。

它不是 append-only：它是**可重建的状态表**（删掉后从 `yongfa.txt` + 后续轮次重新长出来）。由 `chuli` 每轮经由脚本维护，`gengxin` 只读。

```text
# 生命周期表（**维护型**，非 append-only；可从 yongfa.txt 重建）
# 轮次：12
# 满值：10
# 键 | 生命周期 | 最后使用 | 状态
liucheng_biao/H.leak.3 | 3 | 2026-09-27 | 活跃
liucheng_biao/H.cat.1 | 1 | - | 活跃
liucheng_biao/H.old.1 | 0 | 2026-08-01 | 待裁决
liucheng_biao/H.dead.1 | 0 | 2026-07-12 | 已裁决:过期
```

### 规则

- 生命周期是**倒计时**，满值 `L`（默认 10；旧表满值 < 10 时，下次 `--tick` 会自动抬到 10，只升不降）。
- 单位是「轮次」：`chuli` 处理完一个任务 = 一轮。
- 本轮**用到**的键 → 生命周期 = `L`，最后使用 = 当天。
- 本轮**没用**的键 → 生命周期 −1。这就是「零使用触发生命周期标记」。
- 库里存在但表里没有的键（新建 / 首次见到）→ 初始化为 `L`。**所以新条目不会被误判成老废物。**
- 生命周期降到 `0` → 状态 `待裁决` → **必须询问用户**。绝不自动删、绝不自动标过期。
  - 用户同意已无用 → `--expire` → 状态 `已裁决:过期`，冻结，不再倒计时、不重复问。
  - 用户**不同意** → `--refresh` → **生命周期刷新回 `L`**，回到观察。
- 状态只有三种：`活跃` / `待裁决` / `已裁决:过期`。
- **空轮次也要记账**：某个任务全程没用任何知识，也要推进一轮。否则生命周期不会倒计时，「零使用」永远是 0 信息。

### 怎么问用户（MUST：汇总成一次）

归零可能一次几十条（首次启用本机制时，整个库都还没被用过）。**不要逐条连问**，汇总成一次问：

> 「生命周期归零 N 条（列前 10 条 + 总数）。全部标记过期 / 全部保留刷新 / 只处理其中某几条？」

- 答「全部保留」→ 对全部执行 `--refresh`。
- 答「只处理某几条」→ 那几条 `--expire`，其余 `--refresh`。
- **没有答复就不写任何裁决**，状态停在 `待裁决`，下次再问。

### 两种「该退休」的信号，都只是信号

| 信号 | 依据 | 要不要观察期 |
|---|---|---|
| `成=0 且 败>=2` | 确定的失败证据 | 不要，立刻可报 |
| 生命周期归零 | 连续 `L` 轮没人用 | 要（靠轮次累积） |

两者都**只产出「候选」**：用户同意后也只写 `[候选过期]` 标记，**删除永远由用户手动做**（铁律「不删条目」不变）。

## 铁律（MUST）

1. **一个领域一个文件夹**；不得把知识跨领域混放。
2. **只写本领域文件夹内的文件**；不碰别的领域、不碰本 skill 的 SKILL.md。
3. **不删条目**：疑似过期只标 `[候选过期]` + 报告，删除交给用户。
4. **每条保留 `来源`**；无来源的条目不得写入。
5. **幂等**：重复回注同一知识库，结果一致（不重复、不漂移）。
6. **知识库为空 / 缺失 / 不可读 → 不动，只报告**，不凭空生成。
7. **领域不确定就问**，不得臆断归类；非交互且未指定领域时**不写入**，只报告。
8. **禁止本地模型参与本 skill（防污染）**：Ollama / 本地 LLM **不得**执行回注、diff 合并、改 `gengxin_wei` 知识文件（含 `liucheng_biao/`）或索引。本地模型仅允许 `zhishiku-chuli` + `ctf-pwn`（只读库、写题目目录）；`caiji` / `tilian` / **本 skill** 在本地模型模式下**一律禁用**。若当前是本地模型会话 → **停止并报告「gengxin 已禁用（本地模型模式）」**，不得写盘。
9. **执行流只维护两层结构**：新回注不得往 `liucheng_jiu_shupai.txt` 追加；不得把权威步骤只写在无标号的竖排里。执行流权威形态 = `liucheng/`（调用树 diaoyong.txt + 清单 jineng.txt + 技术树 shu/）+ `liucheng_biao/` 卡片；`liucheng.txt` 仅作全标号索引（validate 依赖），**不得删除**。
10. **`yongfa.txt` 只读、只追加**：本 skill 不得合并、改写或删除它的任何行（含历史行）；也不得把它当作知识条目回注。来源计数在条目的 `命中`，实战计数在 `yongfa.txt`，两者不可互写。
11. **`shengming.txt` 只读**：生命周期由 `chuli` 每轮经由 `scripts/yongfa.py` 维护，本 skill 不改。本 skill 只做一件事：把状态已是 `已裁决:过期` 的键，在**下次回注时**于对应条目里落 `[候选过期]` 标记——且**不删条目**。
12. **裁决必须来自用户**：任何情况下都不得自行判定某条生命周期归零的条目「过期」；没有用户答复就停在 `待裁决`。
13. **无快照不回注**：动手改领域文件之前必须先 `snapshot.py --take` 成功。快照失败 → 停下报告，不得先改。
14. **门槛文件两类来源**：`menkan/`（如 `workflow.xml`）只能来自「用户直接提供」或「AI 提取后经用户确认交付」。**AI 自主提取未确认前不得写盘**，只能报告候选；每个 step/point 带 `<source>` 与 `<confirm>`（模板见 `templates/menkan/workflow.xml`）。门槛只写「大概流程」，不得塞具体步骤/命令。
15. **并列候选必走门槛**：树上同一分叉有多个候选且条件同时满足时，先按〔条件〕过滤，再用 `yongfa.py --pick` 按使用次数择一；不得随手挑、不得只按书写顺序而不看使用次数。


### 4 回注前拍快照（MUST）

回注是**覆盖式写**：错误的条目一旦合并进容器，靠人工比对找不回来。所以**动手改文件之前先拍快照**：

```bash
python3 <skill 目录>/scripts/snapshot.py <数据根>/<领域> --take --note "回注 <领域>/<案例id>"
```

- 快照落在 `<数据根>/<领域>/_snap/<YYYYMMDD-HHMMSS>/`，含每个文件的副本 + `MANIFEST.txt`（路径 / 字节数 / sha256）。
- **没拍快照就回注 = 违规**（铁律 13）。快照失败（磁盘满 / 目录不可写）→ 停下报告，不要"先改了再说"。
- 回滚：`python3 .../snapshot.py <领域> --rollback <快照名> --yes`
  - 回滚前会**自动再拍一份** `_snap/<快照名>-preRollback/`，所以回滚本身也可逆。
  - 回滚会把「当前有、快照里没有」的文件移到 `_snap/<快照名>/_orphan-<时间戳>/`，**不删**。
  - 快照自身校验失败（文件缺失 / sha256 不符）→ **拒绝回滚**，避免用坏快照覆盖好现状。
- 清理：`python3 .../snapshot.py <领域> --prune --keep 5`（默认留 5 份）。
- `_snap/` **不是知识目录**：`yongfa.py` / `validate.py` 都不会把里面的副本当成知识条目；回注时也不要把 `_snap/` 当领域文件扫。

### 5 回注后自检（MUST）
回注完成、报告之前，**必须**跑领域库自检脚本（若存在）并处理结果：

```bash
D=<数据根>/<领域>
[ -f "$D/validate.py" ] && python3 "$D/validate.py" || echo "（该领域无 validate.py，跳过）"
```

- 退出码 0 且打印「✅ 全部通过」→ 继续报告。
- 出现 **[错误] ✗** → **不得报告回注完成**：当场修复（缺文件/哨兵异常/引用悬空）后重跑，直到 0。
- 出现 **[警告] ⚠** → 逐条判断：能修则修（补来源/补字段/补卡片引用）；属预期（如新增卡片尚未挂树）则在报告里列出，不阻断。
- 该领域**没有** `validate.py` → 至少手工核对 4 项：必备文件齐、append-only 末尾单 `★`、每条有 `来源`、liucheng 引用的卡片都存在。

> 目的：防止坏数据（哨兵破坏、悬空引用、漏来源）在多次回注中累积；把「体检」固化成回注的收尾动作。

## 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 知识跨领域混放 | 领域文件夹失去意义 | 一个领域一个文件夹 |
| 改了别的领域或 SKILL.md | 污染他人 | 只写本领域文件夹 |
| 删掉 KB 里没有的条目 | 丢知识 | 只标 `[候选过期]` |
| 重复回注同一要点 | 文件膨胀 | 幂等合并，命中累加 |
| 无来源回注 | 不可溯源 | 必须保留来源 |
| 知识库为空仍写入 | 凭空造知识 | 空则不动，只报告 |
| 领域猜错 | 知识进错文件夹 | 不确定就问用户 |
| 回注时重写/合并 `yongfa.txt` | 实战事实被篡改，统计失真 | `yongfa.txt` 只读；它由 chuli 追加 |
| 自行把生命周期归零的条目判为过期 | 越权替用户做决定 | 必须问用户；没答复就停在 `待裁决` |
| 用户答「保留」却忘了刷新生命周期 | 下轮又立刻归零，反复打扰 | 答保留 → `--refresh` 刷新回满值 |
| 没拍快照就回注 | 合并错了无法回退，只能靠人工比对 | 协议第 4 步先 `--take`；失败就停 |
| 回滚时删掉「快照里没有」的文件 | 误删新知识，且不可逆 | `snapshot.py` 只移到 `_orphan-<时间戳>/`，不删 |
| 把 `_snap/` 当领域文件扫 | 同一份知识被重复计数 / 回注 | 跳过 `_snap/`（脚本已内置） |
| AI 提取的门槛未确认就写进 `menkan/` | 凭空门槛污染路由，选枝失真 | 先报告候选 → 用户确认交付 → 才写盘 |
| 门槛文件里塞具体步骤/命令 | 门槛与卡片职责混淆，又臭又长 | 门槛只写大概流程；具体步骤下沉 `liucheng_biao` |
| 多节点同时满足却随手挑一个 | 选枝不可复现、好用的枝被绕过 | 先按〔条件〕过滤 → `yongfa.py --pick` 按使用次数择一 |
| 并列候选只写卡片不写树（或反之） | 两处漂移，选枝看不全候选 | 分叉旁与卡片 `## 并列` 同步维护 |
