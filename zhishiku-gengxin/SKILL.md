# 知识库回注 / 领域分化容器（zhishiku-gengxin）

## 概述

把知识库（`tilian_wei`）里的知识，**按领域**回注到知识容器 `gengxin_wei/` 下对应领域的文件夹。

**一个领域 = 一个文件夹**，知识不跨领域混放。本 skill 只维护 `gengxin_wei/` 里的文件，不动别处。

> 定位：本 skill 是**知识容器 / 素材库**，不是解题器。它把知识按领域沉淀好，供人或 AI 起草领域 skill 时取用。

## 流水线定位

```text
zhishiku-caiji（采集） ─▶ 案例 ─▶ zhishiku-tilian（提炼） ─▶ 知识库
                                                              │ 提炼完成后链式
                                                              ▼
                                          zhishiku-gengxin（按领域回注到容器）
```

| 需求 | 用哪个 |
|---|---|
| 小任务队列 / 每日任务 / 执行次数 | `planing-biao` |
| 长跑项目 / 需求 / issue / 迭代 | `chang-plan` |
| 执行留痕、采集案例 | `zhishiku-caiji` |
| 把案例提炼成知识点 / 执行流 / 错误处理 | `zhishiku-tilian` |
| 用知识库处理某领域任务 | `zhishiku-chuli` |
| **把知识按领域回注到容器** | **本 skill** |

上游：读 `zhishiku-tilian` 的知识库（`tilian_wei`）；上游不可用 → 不写入，报告「未回注」。

## 领域怎么定（关键：问用户）

- 一个领域 = 一个文件夹，名字由用户定义（如 `ctf-pwn`、`web`、`python-env`）。
- 领域来源优先级：
  1. **上游 `zhishiku-tilian` 传入的领域**（首选）→ 直接用；
  2. 调用时参数已指定 → 直接用；
  3. 否则 → **必须询问用户**，不得臆断、不得沿用上次结果。
- 询问时**先列出 `gengxin_wei/` 下已有领域**，让用户选或新建；避免同一领域被写成多个名字（如 `python` 与 `python-env`）。
- 非交互执行且未指定领域 → **不写入，只报告**「待回注的知识 + 建议领域」，等用户下次确认。
- 首次遇到的新领域 → 创建骨架文件夹。

## 数据布局（本 skill 维护的全部文件）

```text
<skill 目录>/xinxi.txt                 # 每个数据根两行：gengxin_wei_win / gengxin_wei_linux
<数据根>/suoyin.txt                    # 全局领域索引（append-only，末尾 ★）
<数据根>/<领域>/
  ├─ tieuli.txt                        # 铁律
  ├─ yuanze.txt                        # 概述原则
  ├─ bianjie.txt                       # 边界
  ├─ cuowu.txt                         # 常见错误
  ├─ liucheng.txt                      # 执行流总览（分诊 + 树形）
  ├─ liucheng_biao/                    # 执行流标号卡片（一步一文件）
  │    └─ <标号>.txt                   # 如 H.leak.5.txt / S.can.3.txt
  ├─ liucheng_jiu_shupai.txt           # 可选：旧竖排备份（只读溯源，不作为回注目标）
  ├─ zhiling.txt                       # 命令速查
  ├─ suoyin.txt                        # 领域索引：来源案例 → 条目（append-only，★）
  ├─ rizhi.txt                         # 更新日志（append-only，★）
  └─ validate.py                       # 领域自检脚本（可选；回注后跑，见协议 7）
```

## 跨平台路径解析（MUST）

`xinxi.txt` 为每个数据根保留**两行**，指向**同一个文件夹**（Windows 与 Linux 双端共享同一份知识容器）：

```text
gengxin_wei_win: <Windows 数据根绝对路径>
gengxin_wei_linux: <Linux 数据根绝对路径>
```

按当前运行环境选取：

- **Windows** → 取 `gengxin_wei_win`（形如 `C:/Users/xi/.pi/agent/skills/...`）。
- **Linux**（含 WSL）→ 取 `gengxin_wei_linux`（形如 `/media/xi/系统/Users/xi/.pi/agent/skills/...`）。
- 旧单行 `<根名>: <路径>` → 按当前 OS 判断是否可访问；不可访问 → 询问用户补写另一平台路径，改回两行格式。

两行必须指向同一份数据根；不一致 → 停下询问，不得自行挑选。

## 领域文件夹骨架（新建领域时生成）

每个 `.txt` 首次创建时写入一行表头 + 尾部哨兵（仅 append-only 的两个文件需要哨兵）：

```text
tieuli.txt     -> # 铁律
yuanze.txt     -> # 概述原则
bianjie.txt    -> # 边界
cuowu.txt      -> # 常见错误
liucheng.txt        -> # 执行流 · 树形总览（含读法 + 入门分诊）
liucheng_biao/      -> # 空目录；回注时按标号落卡片
zhiling.txt         -> # 命令速查
suoyin.txt          -> # 案例id | 产出条目\n★
rizhi.txt           -> # 更新日志\n★
tools/              -> # 该领域专用工具的使用规范（一个工具 = 一个 <工具名>.txt）
```

### `tools/`（领域专用工具）

`<数据根>/<领域>/tools/` 存放**本项目/本领域专用工具的使用规范**，与知识条目分开管理。

- **一个工具 = 一个 `<工具名>.txt`**（如 `libcsearch.txt`）；文件名小写、无空格。
- 每个工具文件至少包含：**何时用（触发条件）/ 安装位置 / 使用规范 / 常见错误 / 边界**。
- **触发时机**：当某个工具在案例里被反复使用、且使用者容易忘记怎么用时，就为其建规范。
- **与 `zhiling.txt` 的区别**：`zhiling.txt` 是「单条命令速查」；`tools/<工具>.txt` 是「工具级的完整使用规范（含环境、消歧、坑）」。简单到一行命令就能表达的不建 tools 文件。
- **回注来源**：由 `zhishiku-tilian` 提炼结果或用户直接指定回注；新建/更新后在 `rizhi.txt` 记一笔。
- **不属于采集指标**：`tools/` 是工具手册，不计入 `suoyin.txt` 的「案例id | 产出条目」统计。

## 条目格式（固定，便于幂等合并）

```text
- <要点一句话>
  来源：<领域>/<案例id> buzou/<NN>.txt 步骤<字母>
  命中：<N>
```

命令速查为表格行，必须带 `来源`。执行流按下方「树形格式」写，卡片与总览都要能溯源。

| 知识库来源 | 归属 / 类型 | 回注到 |
|---|---|---|
| `zhishi/*.txt` | `铁律` | `tieuli.txt` |
| `zhishi/*.txt` | `概述原则` | `yuanze.txt` |

| （工具级完整规范） | 工具手册 | `tools/<工具名>.txt` |

### 执行流树形格式（正式 · 人与 agent 共用）

执行流**不再**以「整文件竖排 1.2.3.」为权威形态。权威形态是：

```text
liucheng.txt            # 总览：读法 + 入门分诊 + 各技术 ASCII 树
liucheng_biao/<标号>.txt # 详解：一步一卡
```

#### 1）`liucheng.txt` 总览结构

```text
# 执行流 · 树形总览
> 读法（人 / agent 相同）：分诊 → 树 → 打开 liucheng_biao/<标号>.txt

## 入门分诊
  （按题面条件选树 A/B/C…；表列：情况 → 进哪 → 卡片）

## 树 X · <技术名>
  ASCII 树；主路径用 │ ▼；分叉用 ├─/└─
  每步标号 + 行内〔时机〕〔条件〕
  分叉旁写清「什么情况走哪枝」

## 其它技术（一笔）
  尚未卡片化的，指向 liucheng_jiu_shupai 或待补
```

#### 2）标号规则

- 形式：`类.段.步` 或 `类.段`（段内唯一）。
- 类：`H` 堆 / `S` 栈 / `F` 格式化 / `T` 通用前置 / 其它自定单字母。
- 例：`H.menu`、`H.leak.5`、`H.hook.trig`、`S.can.3`。
- 文件名 = 标号 + `.txt`（如 `H.leak.5.txt`）。
- **同技术合并**：已有标号则改卡片或在树的分叉上补枝，不另起一套编号。

#### 3）`liucheng_biao/<标号>.txt` 卡片固定字段（MUST）

```text
# <标号> · <一步名称>

## 时机
- 什么时候做这一步（前置已完成什么）

## 条件
- 走本步必须满足的题面/运行条件（可多条）

## 不满足时
- 缺条件时改走哪枝 / 哪张卡 / 或判定为缺口

## 做什么
- 抽象操作；参数用 <占位符>
- 实例：具体命令或 payload 片段

## 参数
- <占位符> 列表

## 下一跳
- 成功 → 哪张卡；失败常见 → 哪条坑 / cuowu

## 来源
- <领域>/<案例id> buzou/<NN>.txt
```

可选：`## 禁止`（anti-hook 后再 add 等）、`## 坑`（短表）。

#### 4）回注规则（替代旧「### 技术模板竖排」）

1. 读 tilian 模板的 `分类` 与步骤 → 判断并入哪棵树（堆/栈/…）。
2. **优先**：为每步分配/复用标号，写入或合并 `liucheng_biao/<标号>.txt`（卡片字段齐）。
3. 同步改 `liucheng.txt`：在对应树挂上该标号，并在枝旁写〔时机〕〔条件〕；新分叉必须写清条件。
4. **公共步骤**进 `T.*` 或分诊，不在每棵树复制。
5. **同一技术**多来源 = 树分叉 / 卡片「条件」补充，不新开平行模板名。
6. 旧 `liucheng_jiu_shupai.txt` **只读**；禁止再往里追加新知识。
7. 领域尚无树形文件时：可用骨架创建空总览 + 空 `liucheng_biao/`；从 tilian 回注时直接写树，不必先写竖排。
8. 每条卡片与总览改动在 `suoyin`/`rizhi` 记来源案例。

#### 5）Agent 可读性（设计意图）

- 树 = **路由**：条件匹配选枝，不必一次读完全库。
- 卡片 = **动作**：字段固定，便于逐步执行与填参。
- 与 `zhishiku-chuli` 约定：先读 `liucheng.txt` 分诊与命中树，再**只打开当前标号卡片**，不要整目录塞进上下文。

## 回注算法

```text
1. 确定本次的领域（参数 / **询问用户**；非交互且未指定则只报告不写入）
2. 定位领域文件夹；不存在则创建骨架
3. 读知识库四类产出，按上面的映射分组
4. 逐条 diff 合并到知识文件（tieuli/yuanze/bianjie/cuowu/zhiling + 执行流树/卡片）：
   - KB 有、文件无        -> 追加（执行流则写/改 liucheng.txt 树节点 + liucheng_biao 卡片）
   - 两边都有（同要点/同标号） -> 取更完整 / 命中更高的一条替换
   - 文件有、KB 无        -> 不删，标 [候选过期] 并在报告列出
5. 追加领域 suoyin.txt 一行（案例 -> 产出了哪些条目）
6. 更新全局 suoyin.txt（该领域的最后更新时间与条目数）
7. 追加 rizhi.txt 一行（append-only）
8. 报告：领域 / 新增 / 更新 / 候选过期
```

## 铁律（MUST）

1. **一个领域一个文件夹**；不得把知识跨领域混放。
2. **只写本领域文件夹内的文件**；不碰别的领域、不碰本 skill 的 SKILL.md。
3. **不删条目**：疑似过期只标 `[候选过期]` + 报告，删除交给用户。
4. **每条保留 `来源`**；无来源的条目不得写入。
5. **幂等**：重复回注同一知识库，结果一致（不重复、不漂移）。
6. **知识库为空 / 缺失 / 不可读 → 不动，只报告**，不凭空生成。
7. **领域不确定就问**，不得臆断归类；非交互且未指定领域时**不写入**，只报告。
8. **禁止本地模型参与本 skill（防污染）**：Ollama / 本地 LLM **不得**执行回注、diff 合并、改 `gengxin_wei` 知识文件（含 `liucheng_biao/`）或索引。本地模型仅允许 `zhishiku-chuli` + `ctf-pwn`（只读库、写题目目录）；`caiji` / `tilian` / **本 skill** 在本地模型模式下**一律禁用**。若当前是本地模型会话 → **停止并报告「gengxin 已禁用（本地模型模式）」**，不得写盘。
9. **执行流只维护树形**：新回注不得往 `liucheng_jiu_shupai.txt` 追加；不得把权威步骤只写在无标号的竖排里而不更新树与卡片。

## 触发（两种）

- **自动（链式）**：`zhishiku-tilian` 提炼完成后，协议最后一步调用本 skill，并传入 `tilian_wei`。
- **手动**：用户说「按知识库更新 <领域> / 回注知识」时。

两种触发都需要领域；参数没给就**问用户**（见上）。

## 协议

```text
- [ ] 1. 确定领域
- [ ] 2. 定位 / 创建领域文件夹
- [ ] 3. 读知识库并按归属分组
- [ ] 4. 逐条 diff 合并到知识文件（含 liucheng 树 + liucheng_biao 卡片）
- [ ] 5. 追加领域 suoyin 与全局 suoyin
- [ ] 6. 追加 rizhi
- [ ] 7. 回注后自检（跑 validate.py）
- [ ] 8. 报告
```

### 7 回注后自检（MUST）

回注完成、报告之前，**必须**跑领域库自检脚本（若存在）并处理结果：

```bash
D=<数据根>/<领域>
[ -f "$D/validate.py" ] && python3 "$D/validate.py" || echo "（该领域无 validate.py，跳过）"
```

- 退出码 0 且打印「✅ 全部通过」→ 继续报告。
- 出现 **[错误] ✗** → **不得报告回注完成**：当场修复（缺文件/哨兵异常/引用悬空）后重跑，直到 0。
- 出现 **[警告] ⚠** → 逐条判断：能修则修（补来源/补字段/补卡片引用）；属预期（如新增卡片尚未挂树）则在报告里列出，不阻断。
- 该领域**没有** `validate.py` → 至少手工核对 4 项：必备文件齐、append-only 末尾单 `★`、每条有 `来源`、liucheng 引用的卡片都存在。

> 目的：防止坏数据（哨兵破坏、悬空引用、漏来源）在多次回注中累积；把「体检」固化成回注的收尾动作。

## 启动自检

- 领域文件夹里 tieuli/yuanze/bianjie/cuowu/liucheng/zhiling + `suoyin.txt` + `rizhi.txt` 齐备；缺则补骨架。若已采用树形执行流，还须有 `liucheng_biao/`（可空）。
- append-only 文件（`suoyin.txt`、`rizhi.txt`）末尾有且仅有一个 `★`。
- 每条待回注条目都有 `来源`，且来源可读。
- 回注后，本领域文件夹之外的文件未发生任何变化。
- **回注后必须跑领域自检**：`python3 <领域>/validate.py`（有则跑；退出码非 0 先修再报告）。

## 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 知识跨领域混放 | 领域文件夹失去意义 | 一个领域一个文件夹 |
| 改了别的领域或 SKILL.md | 污染他人 | 只写本领域文件夹 |
| 删掉 KB 里没有的条目 | 丢知识 | 只标 `[候选过期]` |
| 重复回注同一要点 | 文件膨胀 | 幂等合并，命中累加 |
| 无来源回注 | 不可溯源 | 必须保留来源 |
| 知识库为空仍写入 | 凭空造知识 | 空则不动，只报告 |
| 领域猜错 | 知识进错文件夹 | 不确定就问用户 |
